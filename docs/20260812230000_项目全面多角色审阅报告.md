## 一、总体印象

### 1.1 做得好的地方（先肯定）

1. **DDD 四层边界清晰，依赖方向正确**：domain 层零 infrastructure 引用（仅 `claude-profile` 一处违规），Repository 接口在 domain、实现在 infrastructure；聚合根（Task / MindmapDoc）内聚状态机与不变量校验，应用层只做编排。
2. **TypeScript 纪律严苛**：前端 16k 行**零 `any`、零 `@ts-ignore`**，DTO 全部来自 `@ai-task-flow/shared` workspace 包，前后端契约单一来源。
3. **注释文化堪称模范**：几乎所有非平凡决策都解释 Why 并标注踩坑来源（commit hash / 实测日期），从 `sse-utils.ts` 的"最后一帧没补 `\n\n` 会丢 result 事件"到 `TerminalLauncher.ts` 的"为何用 wt.exe"。这是项目的隐形资产。
4. **并发与崩溃恢复的深思熟虑**（在做了的处）：`AgentRuntime` turnChain 串行化、`projectChatStore` 流所有权 + stale 检测 + 孤儿 sessionId 恢复、`MaimemoService.init` 重置残留 syncing、`ChatService` regenerate 先存新再删旧、`JsonMindmapRepository` tmp+rename 原子写。
5. **构建产物处理教科书式正确**：`backend/public/` **未入库**（已核验 git ls-files = 0），`prepublishOnly` 现场重建 + `files:["public"]` 打包，推翻了"构建产物入库"的常见反模式。
6. **CLI 入口工程质量极高**：端口三段式探测/复用、dev 共存数据竞争告警、前端 dist 多形态解析，是全项目最扎实的部分。

## 二、架构维度

### 2.1 DDD 分层合规性 — 总体良好，一处红线

| 维度 | 评价 |
|------|------|
| domain → infrastructure 依赖 | ✅ 仅 `claude-profile` 违规（见下） |
| Repository 接口/实现分离 | ✅ 6/7 context 遵守；❌ `claude-profile` 在 domain 层无 Repository 接口，Service 直接依赖 `JsonClaudeProfileRepository` 具体类（`ClaudeProfileService.ts:48`） |
| 聚合根内聚 | ✅ Task / MindmapDoc 是典范 |
| 值对象不可变 | ✅ TaskId/Priority/TaskStatus 合格；⚠️ `LlmConfigEntity` / `MaimemoConfig` 只是 interface + 函数，无值对象语义，风格不统一 |

**【🔴 严重 / 架构师】domain 层跨层违规**：`domain/claude-profile/settingsCodec.ts:4` 直接 `import { toWslPath } from '../../infrastructure/system/pathCodec.js'`。这是全项目 domain 层**唯一**的 infrastructure 引用，破坏了 DDD"domain 层可独立编译"的红线。`toWslPath` 是纯函数，应搬到 `_shared` 或 domain 内部。

### 2.2 DI（tsyringe）— 形同摆设，建议二选一

**【🔴 严重 / 架构师】"半套 DI"是纯负担**。`di/container.ts` 只注册 2 个 token 且都被 `useFactory` 绕过；HTTP 入口完全不用 container（`system.ts:108` 注释自承"http 入口不走 DI container"），全靠 `startApp` 手工 `new` 13+ 个 service 透传；`@injectable()` 装饰器挂在多个 Repository 上却几乎无人 `resolve`。

更糟的是 **MCP 进程与 HTTP 进程的装配不对称**：MCP 用 `container.resolve('TaskRepository')` 拿到一个**没注入 eventBus/eventStore/watcher 的默认实例**，与 HTTP 进程操作同一文件却互不通信，且 **MCP 写入的事件不入审计日志**（EventStore 在 MCP 进程完全没写入）。

**建议**：遵循 AGENTS.md 1.1"如无必要勿增实体"，**直接移除 tsyringe**，统一手工装配；或把 `startApp` 的装配搬进 container 让 HTTP + MCP 共享一份 resolve 入口。当前的"两套装配机制并存"既没换来解耦好处，又增加阅读成本。

### 2.3 错误模型 — 不统一，路由层只能靠字符串匹配

mindmap 定义了 4 个类型化错误（`MindmapService.ts:19-48`，是全项目最佳实践模板），vocab 定义 2 个，maimemo 定义 1 个，其余 7 个 service 直接 `throw new Error('...')`。路由层只能靠 message 字符串匹配或 `instanceof` 检测少数几个。

**【🟡 中等 / 架构师】** 在 `_shared` 定义 `DomainError` 基类（带 `httpStatus` 或 `code`），所有 service 抛其子类，路由层用统一 `setErrorHandler` 做错误→HTTP 映射。

### 2.4 并发一致性 — 最值得重构的横向议题

**【🔴 严重 / 架构师】JSON 仓储保护级别四套并存**：

| Repository | writeLock | 原子写(tmp+rename) | 存储内容敏感度 |
|------------|:---:|:---:|---|
| JsonTaskRepository | ❌ | ❌ | 核心业务数据 |
| JsonChatRepository | ❌ | ❌ | 对话历史 |
| JsonClaudeProfileRepository | ❌ | ❌ | **含明文 AUTH_TOKEN** |
| JsonVocabRepository | ✅ | ❌ | 生词本 |
| JsonMindmapRepository | ✅ | ✅ | 思维导图 |

- `JsonVocabRepository.ts:40-47` 与 `JsonMindmapRepository.ts:43-50` 各自**逐字抄了一遍** `withWriteLock`（promise-chain mutex）。
- `JsonTaskRepository.saveAll`（`JsonTaskRepository.ts:110-117`）直接 `fs.writeFile`，写一半崩溃 = **整个 tasks.json 损坏，所有任务全丢，无备份**。
- `loadAll → mutate → saveAll` 非原子，前端连发两个 PATCH 在 async 织入下后写覆盖前写；`taskRoutes.ts:68-72` 用 `findAll → 取最大序号 + 1` 生成 ID，并发创建必然产生重复 ID。

**建议**：抽公共 `JsonRepository<T>` 基类（withWriteLock + 原子写 + fsync），所有 Json*Repository 继承。优先补 Task（核心）和 ClaudeProfile（敏感）。参考 `JsonMindmapRepository.ts:98-104` 已有实现。

### 4.2 关键问题

**【🟡 中等 / 架构师】两套流式架构并存，能力不对称**：
- 新链路（`api/sse-utils.ts:streamAgentEvents` + taskChatStore/projectChatStore）：支持 AbortController、rAF 批量 flush、流所有权、stale 检测。
- 旧链路（`api/chatStream.ts:streamChat` + chatStore + `components/chat/ChatView.tsx`）：**无 AbortController**（`chatStream.ts:7-57` 不接 signal），高频 `text-delta` 逐条 set。

**【🔴 严重 / 资深开发】`ClaudeProfilePanel.tsx`（719 行）新建 profile 的二次保存有竞态 + 脆弱**（`ClaudeProfilePanel.tsx:274-284`）：`create` 不返回 id，靠名字反查 → 重名拿错；两次请求间用户再建同名会错配。根因是后端 `create` 接口缺陷（不支持带 presets 一次创建），用前端脆弱逻辑补。建议后端 `create` 直接收 `apiPresets` 并返回完整对象。同时该文件应拆成 3 个文件。

**【🔴 严重 / 测试】组件测试因 monorepo 双 React 大面积 skip**：`MessageStream.test.tsx` 共 5 个用例**3 个 `it.skip`**，原因是 vitest + monorepo hoist 导致 lucide-react 被 hoist 到根、解析到根 React 18，与 frontend React 19 双实例报错。最复杂的渲染组件（流式消息流）实际无回归保护。

**【🟡 中等 / 资深开发】重型依赖未见懒加载**：`mermaid`、`@uiw/react-codemirror`、`react-syntax-highlighter`、`yet-another-react-lightbox` 全部 eager import，全仓**未见任何 `React.lazy`/`Suspense`/动态 import**。看板首屏不需要 mermaid/codemirror，懒加载能显著减小首屏 bundle。

**【🟡 中等 / 资深开发】uiStore 职责过载**：`uiStore.ts`（167 行）塞了主题/任务选中/创建模式/筛选/安全标志/设置弹窗至少 4 个关注点。`collapsedGroups` 折叠记忆逻辑应独立成 `useBoardGroupingStore`。

**【🟡 中等 / 产品 a11y】键盘可达性不完整**：`KnowledgeTree.tsx:223-238,340-355` 收藏按钮用 `<span role="button" tabIndex={0}>` 但**只绑 onClick 无 onKeyDown**；`FloatingChatWindow.tsx:240-256` 项目 tab 同样问题。键盘用户无法操作。

### 4.3 值得点名的亮点

- **`MessageStream` 的原生虚拟化**（`components/chat/MessageStream.tsx:18-27,331-348`）：用浏览器原生 `content-visibility:auto` + `contain-intrinsic-size` 做不定高列表虚拟化，不卸载 DOM、不测高、无抖动。比上 `react-window` 更优雅。

## 五、工程化维度

### 5.1 CI / 自动化 — 重大缺口

**【🔴 严重 / DevOps】完全没有 `.github/` 目录**：无 workflows、无 Issue/PR 模板、无 CONTRIBUTING、无 SECURITY.md。对一个已在 `package.json` 写了 `repository/homepage/bugs` 指向 GitHub、且 `scripts/publish.sh` 准备发布到 npm 的项目，零 CI 是硬伤。README 顶部的 badges（`tests-52 passed`、`build-passing`）**全部指向空 URL `()`**，是纯装饰性静态徽章，不是真实 CI 状态——在没有 CI 的前提下容易误导。

### 5.2 跨平台脚本 — 突出短板

- **【🟡 中等 / DevOps】`npm run dev` 默认调用 `scripts/dev.ps1`（PowerShell）**，Mac/Linux 用户开箱即崩，必须改用 `npm run dev:bash`。
- **【🟡 中等】`scripts/cleanup.ps1` 仅有 Windows 版**，根 `package.json` 的 `"cleanup"` 脚本非 Windows 无法运行。
- **【🟡 中等】`scripts/dev.sh` 是 `dev.ps1` 的落后分叉**：dev.ps1 已改为 HTTP 探测就绪（tsx watch 重启竞态），dev.sh 仍是旧的端口文件判断，两套脚本长期分叉是维护负担。建议统一到已存在的 `dev:concurrently`（用 `concurrently` 跨平台）。
- **【🟡 中等 / 产品】端口信息自相矛盾**：`README.md:70` 说前端 `:5173`，`dev.ps1:134`/`dev.sh:82` 说 `:5678`，用户照 README 访问会扑空。

### 5.3 依赖与版本管理

- **【🟡 中等 / 架构师】版本号不统一**：root/backend/shared/cli = `0.2.0`，frontend/extension = `0.1.0`。

## 六、安全维度

### 6.1 🔴 spawn 通道安全姿态失控（最严重）

**【🔴 严重 / 安全】`AgentRunner.ts:136` 硬编码 `--permission-mode bypassPermissions`** 进 `baseArgs`，意味着**所有任务对话（`/api/tasks/:id/chat`）和项目对话（`/api/project-chat`）的 claude 都跳过所有权限确认**。这与 `TerminalLauncher.openClaude` 里 `bypassPermissions` 作为"夜间模式可选危险能力"（`system.ts:138` 有 info 日志）的设计意图**直接冲突**——同一个能力，两套截然不同的安全姿态（一个默认开启无日志，一个显式 opt-in 有日志）。始终 bypass = 把 Claude 的文件写/命令执行权限完全放开。

**【🟡 中等 / 安全】`system.ts:131-148` 的 `/api/system/claude-sessions/open` 无 knownRepos 白名单**。`TerminalLauncher.ts:71-82` 用 `start cmd /k "..."` / `start pwsh -Command "..."` 是 shell 字符串拼接，虽然 `projectChatRoutes.ts:117-128` 对 repoPath 做了白名单，但 system 路由没有。本地工具 + 无鉴权 + host=0.0.0.0 = 同网段任意人可注入 `"; rm -rf C:"`。

**建议**：(1) `bypassPermissions` 改为 body 参数显式传入，默认 false，与 TerminalLauncher 对齐；(2) system 路由加 knownRepos 白名单或限制 repoPath 字符集；(3) 危险操作（spawn 终端、storage clear、bypassPermissions）在 `localAccess === false` 时拒绝。

### 6.2 其他安全项

- **【🟢 轻微】全栈无鉴权**：README 已坦诚声明为已知限制，可接受；但危险操作应至少在非本机访问时拒绝（纵深防御）。
- **【🟢 良好】路径穿越防护一致**：`fileRoutes.ts:11-18`、`safePath.ts:12-22`、`ClaudeSessionScanner` 的 sessionId UUID 字符集校验都到位。
- **【🟢 良好】API Key 文件权限 `0600`，GET 接口脱敏，日志 `maskSecret`**。
- **【🟡 中等】`llm-config.json` / `maimemo-config.json` 明文落盘敏感凭证**（GET 已脱敏），建议记录在风险登记册。
- **【🟡 中等】`knowledge-base/` 入库 70 个个人知识笔记**（已核验 `git ls-files knowledge-base | wc -l` = 70），隐私 + 仓库体积 + 与产品定位无关三重问题，应 gitignore 并迁出。

### 8.2 判断

2. **砍/拆聚焦 MVP**：把 vocab/maimemo/mindmap 拆成独立仓库或插件化，把 task + MCP 收敛回真正的 MVP。

**推荐方案 1 + 渐进拆分**：短期改定位（成本最低），中期把与核心无关的模块抽成可选插件（动态注册路由/store），降低耦合。
