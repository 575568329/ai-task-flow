## 二、P0 治理方案（逐条详述）

### P0-1 ｜ AgentRunner 硬编码 bypassPermissions

**报告原文**：`AgentRunner.ts:136` 硬编码 `--permission-mode bypassPermissions`，所有任务/项目对话的 claude 跳过所有权限确认。

**核实证据**：
```ts
// backend/src/application/agent/AgentRunner.ts:128-138
const baseArgs = [
  '-p',
  '--output-format', 'stream-json',
  '--input-format', 'stream-json',
  '--verbose',
  '--include-partial-messages',
  '--permission-mode', 'bypassPermissions',   // ← 协议级固定，用户不可覆盖
  '--max-turns', maxTurns,
];
```
`buildSpawn` 注释「协议级固定参数（对齐 multica buildClaudeArgs，用户不可覆盖）」。

**根因**：`bypassPermissions` 被当作「协议必备参数」而非「危险能力」。同一项目里 `TerminalLauncher`（`system.ts` 通道）把它当 opt-in 显式能力并有 info 日志，**两套安全姿态自相矛盾**。

**影响范围**：
- AgentRunner（spawn CLI 模式）服务于**任务对话**（`/api/tasks/:id/chat`）和**项目对话**的旧链路。
- 注：常驻 `AgentRuntime`（SDK 模式，`AgentRuntime.ts`）走的是 inline Settings，未必走这条路径——实施时需确认当前哪条链路在线，避免「改了死代码」。

**修复方案 🛠️**：

1. `AgentRunOptions` 增加显式开关：
```ts
// application/agent/AgentRunner.ts
export interface AgentRunOptions {
  // ...existing
  /** 显式开启 claude 权限旁路。默认 false，与 TerminalLauncher 安全姿态对齐。 */
  bypassPermissions?: boolean;
}
```

2. 把 `--permission-mode` 移出 baseArgs，按开关注入：
```ts
const baseArgs = [
  '-p', '--output-format', 'stream-json', '--input-format', 'stream-json',
  '--verbose', '--include-partial-messages',
  '--max-turns', maxTurns,
];
// 危险能力显式 opt-in，默认不旁路
if (opts.bypassPermissions) {
  baseArgs.push('--permission-mode', 'bypassPermissions');
}
```

3. 调用方（任务对话 / 项目对话路由或 service）显式传 `bypassPermissions`，并在**非默认开启**前提下加一行 FileLogger 告警：
```ts
if (opts.bypassPermissions) {
  logger.warn({ sessionId }, 'agent 旁路权限已开启');
}
```

4. 前端只在用户**显式勾选「夜间模式/信任模式」**时才下发该字段（与 TerminalLauncher 的 UI 开关一致）。

**工作量 ⏱️**：0.5h（含调用方对齐 + 1 个单元测试：`bypass=false` 时 args 不含该 flag）。

**验证**：
- 单测断言 `buildSpawn({..., bypassPermissions: false}).args` 不含 `bypassPermissions`；`true` 时含。
- 人工：默认对话不旁路，勾选后旁路且日志可见。

**风险 🔒**：默认关闭后，claude 在任务对话里遇到需要权限的操作会**卡住等确认**（stream 模式下表现为无 result 事件）。需配套：要么前端给「信任此任务」开关，要么 claude settings 里预置宽松规则（见 `cleanSettings.ts`）。**建议默认 false，但提供前端开关**，而非简单删除。

### P0-2 ｜ spawn 通道 + 默认 host 安全收敛

**报告原文**：`system.ts:131-148` 无白名单；host=0.0.0.0 无鉴权 = 同网段任意人可命令注入。

**核实证据**：
```ts
// backend/src/http-server.ts:124
const host = options.host ?? process.env.HOST ?? '0.0.0.0';   // ← 默认监听所有网卡

// backend/src/interfaces/http/routes/system.ts:132
const { repoPath, env, sessionId, bypassPermissions } = request.body ?? {};
//   repoPath 未经白名单校验，直接喂给 TerminalLauncher（start cmd /k "...", shell 拼接）
```
对比 `projectChatRoutes`（报告指出 :117-128 有白名单），system 路由确实缺失。

**根因**：
- (a) 默认 host `0.0.0.0` 是「方便扩展/局域网」的默认，与「本地工具无鉴权」叠加成攻击面。
- (b) system 路由复用了 `projectChatRoutes` 的终端能力但**没复用其白名单**。

**修复方案 🛠️**（分两步，可独立提交）：

**步骤 A：默认 host 收敛到 127.0.0.1**
```ts
// backend/src/http-server.ts:124
const host = options.host ?? process.env.HOST ?? '127.0.0.1';
```
需要局域网访问时显式 `HOST=0.0.0.0` 启动，并在控制台打印**告警**：
```ts
if (host === '0.0.0.0') {
  console.warn('⚠️ 监听 0.0.0.0：服务无鉴权，同网段可访问全部接口（含 spawn 终端）。仅限隔离网络。');
}
```

**步骤 B：system 路由加白名单 + 非本机拒绝**
```ts
// system.ts —— 抽取与 projectChatRoutes 同源的校验
function assertKnownRepo(repoPath: string) {
  if (!KNOWN_REPOS.includes(repoPath)) {
    throw new Error(`非法 repoPath: ${repoPath}`);
  }
}
// 在 /claude-sessions/open handler 顶部
assertKnownRepo(repoPath);
// 危险操作（spawn 终端 / bypass / storage clear）非本机访问一律拒绝（纵深防御）
if (!isLocalAccess(request) && isDangerous) {
  return reply.code(403).send({ error: '危险操作仅限本机' });
}
```
- `isLocalAccess`：复用 `server.ts:161` 已有的 `ip === 'localhost'` 判断（抽公共）。
- `KNOWN_REPOS`：从配置/扫描结果来，与 `projectChatRoutes` 统一来源（避免白名单两处维护）。

**工作量 ⏱️**：步骤 A 5min；步骤 B 1h（含抽公共白名单来源 + 单测）。

**验证**：
- 默认启动 `netstat` 确认监听 127.0.0.1。
- 单测：非法 repoPath 返回 400/403；`isLocalAccess=false` + spawn 返回 403。

**风险 🔒**：host 改 127.0.0.1 后，**扩展若运行在非本机或通过局域网访问将失效**。Chrome 扩展 service worker 访问 localhost 走的是本机回环，不受影响（`server.ts:109-121` 已处理 PNA）。需在 README 注明「局域网访问需显式 HOST=0.0.0.0」。

### P0-3 ｜ 统一 JSON 仓储并发保护

**报告原文**：四套保护级别并存；Task/Chat/ClaudeProfile 无锁无原子写，崩溃即损坏全量数据。

**核实证据**：
```
JsonTaskRepository.ts:114          await fs.writeFile(this.filePath, raw);
JsonChatRepository.ts:118          await fs.writeFile(this.filePath, JSON.stringify(data, null, 2));
JsonClaudeProfileRepository.ts:76  await fs.writeFile(this.filePath, JSON.stringify(data, null, 2), 'utf-8');
JsonMindmapRepository.ts:43,100    有 withWriteLock + tmp+rename（教科书级实现）
```

**根因**：仓储分批实现，各自抄了一遍（或不抄），没有横向抽象。`JsonMindmapRepository` 文件头注释已完整论证了「为什么需要锁 + 原子写」，是现成范本。

**影响范围**：
- **Task**：核心业务数据，`loadAll → mutate → saveAll` 非原子，前端连发 PATCH 后写覆盖前写；`taskRoutes` 用「取最大序号 +1」生成 ID，并发必重复。
- **ClaudeProfile**：存储**含明文 AUTH_TOKEN**，损坏/竞态影响最敏感。
- **Chat**：对话历史，量大。

**修复方案 🛠️**：抽公共 `JsonRepository<T>` 基类，所有 Json*Repository 继承。

```ts
// backend/src/infrastructure/persistence/JsonRepository.ts
import { promises as fs } from 'node:fs';
import * as path from 'node:path';

/**
 * JSON 文件仓储基类：统一并发保护 + 原子写。
 *  - withWriteLock: promise-chain mutex，串行化 loadAll→改→saveAll（摘自 JsonMindmapRepository）。
 *  - 原子写: 先写 .tmp 再 rename（POSIX 原子），写崩只留孤儿 tmp，主文件不损。
 *  - fsync: 保证数据落盘（而非 OS page cache），防断电丢半。
 */
export abstract class JsonRepository<T> {
  protected constructor(protected readonly filePath: string) {}

  protected async loadAll(): Promise<T[]> { /* 读文件 → JSON.parse，文件不存在返回 [] */ }
  protected async saveAll(data: T[]): Promise<void> { /* withWriteLock + 原子写 + fsync */ }

  /** 子类用：在锁内执行「读→改→写」事务。 */
  protected withWriteLock<U>(task: () => Promise<U>): Promise<U> { /* 同 Mindmap 实现 */ }
}
```

各仓储改造（以 Task 为例）：
```ts
export class JsonTaskRepository extends JsonRepository<TaskRow> implements TaskRepository {
  // saveAll 调用从 fs.writeFile 改为 super.saveAll（继承原子写）
  // create/findAll 等用 withWriteLock 包裹「读序号→生成 ID→写」事务，根治并发重复 ID
}
```

**实施顺序**（按敏感度）：
1. `JsonClaudeProfileRepository`（含明文 token，最高优先）
2. `JsonTaskRepository`（核心数据 + 并发 ID 问题）
3. `JsonChatRepository`
4. （Vocab/Mindmap 已有，后续重构为继承基类，行为不变）

**工作量 ⏱️**：基类 1.5h；每仓储改造 + 测试 1h × 3 ≈ 3h；合计约 **0.5 天**。

**验证**：
- 并发测试：N 个并发 `saveAll`，断言最终状态一致（Mindmap 已有该测试范式可抄）。
- Task 专项：N 个并发 `create`，断言无重复 ID。
- 崩溃模拟：写入中 `process.kill`，重启后文件可正常 load（.tmp 残留不影响主文件）。

**风险 🔒**：低。基类行为对齐已有 Mindmap 实现，是「推广现有正确做法」。注意 Windows 上 `fs.rename` 跨盘符会失败——`tmp` 必须与目标**同目录**（`path.dirname(filePath)`），Mindmap 实现已遵守，基类沿用。
