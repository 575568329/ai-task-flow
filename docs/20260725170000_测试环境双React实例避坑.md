# 测试环境避坑:vitest + monorepo hoist 双 React 实例

- **日期**:2026-07-25
- **环境**:Windows 11 / Node 22 / npm workspaces / frontend react@19 + 根 node_modules react@18
- **触发任务**:悬浮窗历史会话体验优化(commit `6e7cf74`),给 `MessageStream` 引入 `@tanstack/react-virtual` 做虚拟滚动
- **结论**:产品构建完全正常,仅单测炸;根因是 monorepo hoist 让被测组件解析到根 react@18,与 frontend react@19 形成**两个 React 实例**。最终**换零依赖方案(content-visibility:auto)绕开**,未做深度治理。

> 同类根因(monorepo hoist)的**构建时**表现(vite tsc 类型冲突)见
> [20260723130001_项目避坑与约定.md](20260723130001_项目避坑与约定.md) 第十一节。本文专讲**测试时**。

---

## 一、症状(报错清单,任一命中即疑似双实例)

| 报错 | 触发场景 |
|------|---------|
| `Cannot read properties of null (reading 'useReducer')` | 渲染任何带 hook 的被测组件 |
| `An older version of React was rendered`(后跟一大段 invariant 文本) | 被测树里混入了 react@18 渲染的子树 |
| `Function components cannot be given refs` | react-resizable-panels / radix 等 forwardRef 组件 |

特征:**只在 `vitest` 里炸**,`npm run build` / `npm run dev` 完全正常。

---

## 二、根因(hoist + externalize 两件事叠加)

### 根因一:hoist 把被测依赖的 react peer 解析到根 18

monorepo 里:

| 位置 | react 版本 | 谁用 |
|------|-----------|------|
| 根 `node_modules/react` | **18**(extension 用) | 被 hoist 的包的 peer 默认解析到这里 |
| `frontend/node_modules/react` | **19** | frontend 自身代码解析到这里 |

当 frontend 引入的某个包 P(`@tanstack/react-virtual` / `react-markdown` / `lucide-react` / `remark-*` / `rehype-*`)被 **npm hoist 到根 node_modules** 时,P 内部的 `require('react')` 解析到**根 18**;而 frontend 自己写的组件解析到 **frontend 19**。同一棵被测树里出现两个 React 实例 → hooks invariant 炸。

> 注意:**不是所有包都会被 hoist**。只有当 P 不与根的其他声明冲突、且 npm 认为 dedupe 有利时才提升。所以"同一个项目里 A 组件能测、B 组件炸"是常态,取决于 B 依赖的包是否被 hoist。

### 根因二:vitest 把 node_modules externalize,绕过了 dedupe

`frontend/vite.config.ts` 有:

```ts
resolve: { dedupe: ['react', 'react-dom'] }
```

这让**产品构建(vite)**强制单一 React,所以 dev/build 永远没事。

但 **vitest 默认把 node_modules 里的包 externalize**(交给 Node 原生 resolve),这些包**不进 vite 的转换链**,因此 `dedupe` / `resolve.alias` 对它们**不完全生效**。

`frontend/vitest.config.ts` 已经写了很激进的 react 正则 alias:

```ts
{ find: /^react$/,           replacement: frontendReact },
{ find: /^react\/(.+)$/,     replacement: `${frontendReact}/$1` },
{ find: /^react-dom$/,       replacement: frontendReactDOM },
{ find: /^react-dom\/(.+)$/, replacement: `${frontendReactDOM}/$1` },
```

注释承诺"**彻底消除两份 React**"。**但实战不成立**:对被 externalize 的 node_modules 包(即根因一里被 hoist 的 P),vitest 在 resolve 它们内部 `require('react')` 时不走这套 alias → 仍拿到根 18。

> ⚠️ 这条是本次最值钱的结论:**vitest.config.ts 的 react alias 只对 vite 转换的模块(你自己的 src、alias 进来的包)生效,对 externalize 的 node_modules 无效**。注释里"彻底消除"是高估,别再盲信。

## 三、验证过、无效的尝试(别再浪费时间)

下面这些**都没能**解决被 hoist 包的双实例(只对部分场景缓解):

1. `npm install jsdom` 换环境(node → jsdom)—— 与双实例无关。
2. 在 `vite.config.ts` 的 `test` 块加配置 —— **vitest 根本不读 vite.config.ts 的 test 块**(见配套教训一)。
3. `test.deps.inline: [...]` —— 对部分包有效,但对 react-markdown 这类深依赖链仍漏。
4. `ssr.noExternal: [...]` —— 同上,externalize 边界难穷举。
5. 加密 react 正则 alias(现 vitest.config.ts 已是最激进形态)—— 见根因二,对 externalize 包无效。

**结论:在 vitest 层面"治本"成本极高,且脆弱(新加一个被 hoist 的包就复发)。推荐绕开。**

## 四、解决方案(按优先级,先看 1)

### ✅ 方案 1:换零依赖方案,绕开触发 hoist 的包(本次采用)

最省心。本次把 `@tanstack/react-virtual` 换成浏览器原生虚拟化:

```tsx
// 屏幕外节点跳过渲染,等价于虚拟滚动的"只渲染可见区",但零依赖
const turnContainerStyle: CSSProperties = {
  contentVisibility: 'auto',
  containIntrinsicSize: 'auto 120px', // 预估高度,避免滚动条抖动
};

{turns.map((t) => (
  <div key={t.id} style={turnContainerStyle}>
    <TurnRow turn={t} />
  </div>
))}
```

配合 `React.memo(TurnRow)`,流式追加时只重渲最后一轮。数百条消息滚动流畅,且不引入任何会被 hoist 的包。

> 适用前提:你的"虚拟滚动"需求只是"长列表不卡",不需要精确 DOM 回收。content-visibility 让浏览器自己跳渲染,效果足够。

### 🟡 方案 2:测试里 stub 掉触发冲突的图标/组件

无法换包时,把"在测试树里渲染 react@18 子树"的入口 mock 掉。本次给两个测试文件加了:

```ts
// MessageStream.test.tsx —— MessageContent 内含 react-markdown 链,被 hoist
vi.mock('@/components/chat/MessageContent', () => ({
  MessageContent: ({ content }: { content: string }) => <div>{content}</div>,
}));

// SessionList.test.tsx —— lucide-react 被 hoist
vi.mock('lucide-react', () => ({ Plus: () => null }));
```

要点:**stub 到"被测组件之下"**,把整条 react@18 渲染链掐断在被测组件之外。`lucide-react` 这类纯图标库 mock 成 `() => null` 零副作用。

### 🔴 方案 3:无法 stub 的用例 `it.skip` + 写明原因

```tsx
// TODO(测试环境): vitest + monorepo hoist 双 React 实例 —— lucide-react(Copy 图标)
// 被 hoist 到根 → 解析到根 react 18,footer 含 Copy 触发 "older version of React"。
// vitest.config.ts 的 react alias 对 externalize 包不完全生效。
// 产品构建 vite dedupe 生效不受影响,待专项治理后启用。
it.skip('非流式时点击复制触发 onCopyLast', () => { ... });
```

**必须**在 skip 注释里写清:触发包、为什么、产品是否受影响、何时回头。否则 skip 就是隐形债。

## 五、配套教训(本次额外踩的)

### 教训一:vitest 优先读 `vitest.config.ts`,**不读** `vite.config.ts` 的 test 块

曾经把测试配置写进 `vite.config.ts` 的 `defineConfig({ test: {...} })`,折腾很久发现不生效。**vitest 检测到独立的 `vitest.config.ts` 后,完全以它为准**,`vite.config.ts` 里的 test 块被忽略。

> 动测试配置前先确认改的是哪个文件。两个都存在时,`vitest.config.ts` 赢。

### 教训二:vitest 1.6.1 的 `setupFiles` 里设 `afterEach` **不跨文件生效**

`@testing-library/react` 的自动 cleanup 依赖全局 `afterEach`。在 `src/test/setup.ts` 里写 `afterEach(cleanup)` 只对部分场景生效,跨测试文件不可靠 → 出现 `Found multiple elements with the text: xxx`(上一个用例的 DOM 没清)。

**可靠做法:在每个测试文件顶部显式写**:

```ts
import { afterEach } from 'vitest';
import { cleanup } from '@testing-library/react';
afterEach(cleanup);
```

### 教训三:compaction / 接手后,先 `git log` + 查现有配置,别假设从零

本次最大的隐性浪费:会话压缩后丢失"前序会话已配好 `vitest.config.ts`(react alias)+ `src/test/setup.ts`"的上下文,误判为新环境,又写了一份 `vite.config.ts` test 块 + `src/test-setup.ts`(vitest 根本不读),空转一圈。

> 接手任何测试/构建配置任务,第一动作:`git log --oneline -- frontend/vitest.config.ts frontend/src/test/` + 读现有文件。**trust the ledger and `git log` over your own recollection.**

## 六、快速判断"是不是这个坑"

1. 报错含 `useReducer` / `older version of React` / `given refs` + **只在 vitest 炸、build 正常** → 基本就是。
2. `npm ls react` —— 看 frontend 与根的版本是否不同(本项目:frontend 19 / 根 18)。
3. 看报错涉及的包是否在**根** `node_modules`(被 hoist):
   ```bash
   ls node_modules/<嫌疑包> 2>/dev/null && echo "被 hoist(高危)"
   ```
4. 临时把嫌疑包 `vi.mock` 成空实现,报错消失 → 确诊。

## 七、遗留(待专项治理)

本次采用方案 1(content-visibility)+ 方案 2(stub)+ 方案 3(1 个 skip)组合,未做"vitest 层彻底单实例"治理:

- `MessageStream.test.tsx`:1 个用例 `it.skip`("复制"按钮,因 lucide Copy 图标)。产品构建不受影响。
- `vitest.config.ts` 的 react alias 注释仍写"彻底消除两份 React",**与实战不符**,建议下次治理时同步修订注释,避免误导。

**何时回头**:若未来 frontend 再引入多个被 hoist 的 UI/markdown 依赖、skip 用例积累到影响回归信心时,再立项做 vitest 单实例治理(可探索 `vitest` 的 `server.deps.inline` 全量化 + 自定义 conditions,或评估迁移到对 monorepo hoist 更友好的 test runner)。
