# 工作记录重构：版本 → 需求 → 条目 + 知识库关联

> 日期：2026-11-23（2026-11-23 多角色评审后修订）
> 状态：已评审，待实施
> 范围：worklog 数据模型与 MCP 接口、前端树、数据迁移、知识库元数据与多视图

## 1. 背景

### 1.1 当前模型的问题

现有结构是「项目 → 版本 → 条目」，版本挂在项目下。实测数据：

| 版本 | 分布 |
|---|---|
| V8.0.5 | 搜题平台 10 条 + 资源加工平台 8 条 |
| V8.0.6 | 搜题平台 4 条 + 资源加工平台 5 条 |
| V8.0.8 | 组卷 11 条 + 资源加工平台 8 条 + 题库 1 条 |

同一个迭代版本被项目树切碎，查「V8.0.8 做了什么」必须分别打开三个项目。同时缺少「需求」这一工作单元：一个需求通常包含多次改动、跨多个项目，现在只能靠标题和 `relatedProjects` 零散表达。

### 1.2 目标模型

```
主题（建设计划，如「澳门底层数据建设」「大陆数据建设」）
  └─ 版本（迭代/发布，如 V8.0.8）
       └─ 需求（工作单元，关联项目）
            └─ 条目（一次具体改动，记录实际项目/文件/diff/阶段）
```

- **主题**是顶层建设计划（澳门/大陆等），全局唯一，包含多个版本。
- **版本**是时间与发布维度的主线，归属于一个主题，全局唯一（V8.0.8）。
- **需求**是版本内的工作单元，一个需求可关联多个项目。
- **条目**是流水记录，保留实际改动的项目、stage、文件与 diff。

> 2026-11-24 修订：原设计只有「版本→需求→条目」，把「澳门底层数据建设」错放成了每个版本下的需求。
> 现新增顶层主题，版本归属主题；旧数据把该需求提升为主题并保留同名需求承载旧条目。

### 1.3 创建规则（用户明确要求）

- **AI 不得自动创建版本或需求**。
- 版本与需求由用户在页面手动创建，创建后生成可复制的唯一 id（`v_xxx` / `r_xxx`）。
- 用户把 id 告诉 AI，AI 只能写入指定版本/需求；id 不存在时明确报错并提示先创建。
- AI 可以查询现有版本/需求，帮用户确认写法，但**不提供写接口**。

### 1.4 破坏性变更与沟通

本次是破坏性重构，必须显式处理：

1. **MCP 签名变更**：`record_work` 从 `project + version` 改为 `versionId + requirementId`，旧会话/旧提示词会直接失败。
   - 错误信息必须写：「版本/需求需由用户在页面创建并复制 id；不要自行创建或猜名称」。
   - 工具描述同步强调。
   - README / `.claude/CLAUDE.md` 标注「旧会话需重连 MCP」。
2. **数据不可被旧代码读取**：迁移后移除 `projects[].versions`，旧版后端读新数据会空。
   - 明确声明：**不支持回滚到旧代码**；迁移前备份 `worklog.json`，回滚只能恢复数据文件 + 旧代码，二者必须同时回退。
3. **工具数量 12 → 14**（新增 `list_versions` / `list_requirements`），`docs/mcp-registration.md`、catalog、stdio 冒烟测试同步更新。

## 2. 数据模型

```ts
interface WorklogData {
  /** 项目字典:名称、稳定 id、归属路径;不再作为树根 */
  projects: WorklogProject[];
  /** 建设主题(顶层):澳门/大陆等建设计划 */
  programs: WorklogProgram[];
  /** 版本扁平存储,通过 programId 归属主题 */
  versions: WorklogVersion[];
}

interface WorklogProgram {
  id: string;              // g_xxx
  name: string;            // 全局唯一,如「澳门底层数据建设」
  description?: string;
  createdAt: number;
}

interface WorklogVersion {
  id: string;              // v_xxx
  name: string;            // 全局唯一,如 V8.0.8
  programId: string;       // 所属主题
  description?: string;
  createdAt: number;
  requirements: WorklogRequirement[];
}

interface WorklogRequirement {
  id: string;              // r_xxx
  title: string;           // 需求名称,版本内唯一
  description?: string;
  /** 需求级关联项目(名称快照 + id) */
  projects?: string[];
  projectIds?: string[];
  createdAt: number;
  entries: WorklogEntry[];
}

interface WorklogEntry {
  id: string;
  title: string;
  detail: string;
  /** 本条实际改动的项目(由路径归属或显式传入) */
  project?: string;
  projectId?: string;
  files?: WorklogEntryFile[];
  diff?: string;
  tags?: string[];
  stage?: WorkStage;
  sourcePath?: string;
  pathUnmatched?: boolean;
  relatedProjects?: string[];   // 保留:条目级补充关联
  relatedProjectIds?: string[];
  date: string;
  createdAt: number;
  updatedAt: number;
}
```

### 2.1 唯一约束

- 主题名全局唯一。
- 版本名全局唯一（跨主题也不重复）。
- 需求名在版本内唯一。
- 项目名仍全局唯一（字典键）。
- 每个版本必须归属一个已存在的主题。

> 命名空间：当前假设单产品线，`V8.0.8` 全局唯一。若将来出现多产品线重名，版本名允许 `产品线/V8.0.8` 形式；本期不做。

### 2.2 需求范围与条目实际项目

需求级 `projects` 是**计划范围**，条目级 `project` 是**实际改动**，两者可能不一致：

- 条目 `project` 以路径归属/显式传入为准，不因需求范围而拒绝写入。
- 两者不一致时，需求详情显示提示：「存在范围外改动：<项目名>」。
- 不自动把实际项目加入需求范围（避免需求范围被静默扩大）。

## 3. MCP 接口

| 工具 | 变更 |
|---|---|
| `record_work` | 必填改为 `versionId`、`requirementId`、`title`、`detail`、`stage`；`project` 改为可选：不传时由路径归属推断，传入时必须是已存在的项目名（不自动创建）。id 不存在 → 报错并列出可选 id/名称 |
| `query_work` | 支持 `versionId` / `requirementId` / `project` / `stage`；结果附带主题、版本与需求名称 |
| `list_programs` | 新增：列出建设主题（id、名称、版本数、条目数） |
| `list_versions` | 新增：列出版本（id、名称、所属主题、需求数、条目数、首末日期）；可按 `programId` 过滤 |
| `list_requirements` | 新增：按版本列出需求（id、名称、关联项目、条目数） |
| `update_work` / `delete_work` | 不变（按 entryId） |
| `delete_version` / `delete_project` | 语义调整：删除版本即删其需求与条目；删除项目只从字典移除，不删历史记录 |
| 版本/需求创建 | **不提供 MCP 写工具**，仅页面 |

工具描述（catalog）同步：明确「版本/需求必须由用户先建，AI 传 id；不要尝试创建或猜名称」。

## 4. 前端

### 4.1 树

```
澳门底层数据建设                [复制 id] [新建版本]
  ├─ 版本 V8.0.8                [复制 id] [新建需求]
  │    ├─ 澳门底层数据建设        [复制 id]
  │    └─ 推荐基本学力修复
  └─ 版本 V8.0.7 …
大陆数据建设 …
```

- 条目仍在右栏展示，树到需求级。
- 每个节点可复制 id（沿用现有 `CopyIdButton`）。
- 顶部操作：「新建版本」。
- 需求节点右键：「新建需求」「重命名」「删除」。

### 4.2 筛选与展示

- 项目筛选：按条目/需求的 `project` 过滤（保留现有下拉）。
- 阶段筛选：条目 `stage`。
- 关联项目：条目/需求的 `relatedProjects`。
- 条目卡片显示：实际项目、阶段、关联项目、id。

### 4.3 新建流程与 id 可达性

- 新建版本：输入名称 + 描述 → 生成 `v_xxx` → 树中出现 → 复制 id 给 AI。
- 新建需求：在选中版本下输入名称 + 关联项目（多选）→ 生成 `r_xxx` → 复制 id 给 AI。

id 是 AI 记录的唯一入口，必须随时可取，不能只出现在创建弹窗里：

- 创建成功的 toast 里直接带「复制 id」按钮。
- 树节点常驻复制按钮（沿用 `CopyIdButton`）。
- 需求详情/工具栏同样提供复制入口。
- 复制文案统一为纯 id（`v_xxx` / `r_xxx`），不要带前缀文字，方便直接粘贴给 AI。

## 5. 数据迁移

一次性、幂等、HTTP 启动时执行（沿用现有迁移锁协议）：

1. **按版本名归并**：把所有 `projects[].versions[]` 按 `name` 合并为顶层 `versions[]`；同名版本的条目进入同一版本。
2. **每个版本建一个需求**，标题固定为 `澳门底层数据建设`；该版本下所有旧条目挂入。
3. **提取建设主题（迁移 v2）**：对每个版本，若其需求中存在标题为「澳门底层数据建设」的，则以该标题聚合主题（同名只建一个）；否则归入默认主题「未分类建设」。所有版本写入 `programId`。
4. **条目补齐 project**：原所属项目名写入 `entry.project`，并尽量映射 `projectId`。
5. **生成 id**：主题 `g_`、版本 `v_`、需求 `r_` + 短随机。
6. **保留旧结构快照**：迁移前备份 `worklog.json`（`worklog-backups/`，滚动 10 份）；写入标记 `.migration-version-tree.json`（v1）与 `.migration-program-layer.json`（v2），均原子写。
7. 迁移不删除任何条目；旧 `projects[].versions` 字段迁移后移除；版本内保留同名需求承载旧条目。

> 幂等口径：以**数据形态**判定，不看标记文件 gate——只要还存在旧 `projects[].versions` 就迁移，迁移后数据原样返回，第二次执行 `skipped: true` 且工作记录文件字节不变。标记仅记录执行时间，可删除后重跑（重跑对已迁移数据无副作用），也便于旧进程回写旧结构时自动自愈。

> 说明：`worklog-template`、`v0.3.0` 等非业务版本同样按上述规则迁移，保持数据完整。

### 5.1 回滚

迁移后旧结构被移除，**旧代码无法读取新数据**。回滚必须同时满足：

1. 恢复迁移前的 `worklog.json` 备份；
2. 回退到迁移前的代码版本。

只做其中一项会导致空树或数据错读。迁移脚本与设计文档需明确此约束。

## 6. 知识库改造

### 6.1 存储

- 统一到 `resolveDataDir()/knowledge-base/`（现状：`~/.ai-task-flow/knowledge-base` 8 篇；项目内 `./knowledge-base` 67 篇为孤儿数据）。
- 提供一次性导入：把项目内 67 篇复制到数据目录（**不删除原目录**，作为回滚源）。
- 冲突处理：同名文件保留两份，导入版加 `-imported` 后缀；导入结束输出冲突清单（原路径 → 新路径）。
- 文件仍按主题目录存放（技术方案/工作日志/架构设计…），不按版本搬家。

### 6.2 元数据

文档 frontmatter 增加可选关联：

```yaml
---
title: xxx
versionId: v_xxx
requirementId: r_xxx
projectId: p_xxx
stage: dev
tags: [架构设计]
---
```

- `save_to_knowledge` 增加上述可选参数；缺省不关联。
- 关联字段只做「软关联」：被删除的版本/需求不做级联，展示为「已删除」。

### 6.3 树与视图

左侧树支持切换视图（单选，记忆上次选择）：

| 视图 | 组织方式 |
|---|---|
| 按分类（默认） | 现有目录树 |
| 按版本 | 版本 → 需求 → 文档（未关联文档归「未关联」） |
| 按项目 | 项目 → 文档 |
| 按阶段 | 阶段 → 文档 |

- 文档可同时在多个视图中出现；切换只影响树的组织，不影响存储。
- 搜索、标签筛选在所有视图下保持可用。
- 视图中显示「已关联 N / 未关联 M」；未关联文档统一进入「未关联」分组，避免切换到版本视图时误以为文档丢失。
- 上线初期可先只开放「按分类 / 按项目」，待 frontmatter 元数据积累后再开放「按版本 / 按阶段」。

## 8. 错误与边界

| 场景 | 处理 |
|---|---|
| AI 传入不存在的 versionId/requirementId | 报错，返回现有 id 与名称列表，提示用户先创建 |
| requirementId 不属于指定 versionId | 报错「需求不属于该版本」，列出该版本下的需求 |
| versionId 指向已删除版本 | 报错「版本已删除」，提示重新创建 |
| 版本名重复创建 | 拒绝 |
| 需求名在版本内重复 | 拒绝 |
| 删除主题 | **强制输入主题名确认**；级联删其版本/需求/条目（先备份）；入口放二级菜单 |
| 新建版本 | 必须选择已存在的主题；主题不存在则拒绝并列出可选主题 |
| 删除版本 | **强制输入版本名确认**；删其需求与条目（先备份）；入口放二级菜单 |
| 删除项目 | **语义变更（破坏性）**：只从项目字典移除，不再删除其历史条目；条目保留项目名称快照，路径归属失效。页面需明确提示 |
| 创建需求 | 关联项目必须已存在；不存在则拒绝并列出可选项目 |
| 知识库关联 id 不存在 | 拒绝写入该字段或降级为不关联并提示，不阻断文档保存 |
| 迁移重跑 | 按数据形态判定（存在旧 `projects[].versions` 才迁移）；已迁移则 `skipped: true`、文件字节不变；标记 `.migration-version-tree.json` 仅记录执行时间，可删除后重跑 |
| 知识库文档关联的版本被删 | 显示「已删除关联」，文档保留 |

## 9. 测试

**迁移矩阵**（必须逐项覆盖）：

| 场景 | 期望 |
|---|---|
| 同名版本跨 3 个项目 | 归并为一个版本，条目全保留 |
| 版本下无条目 | 仍生成版本与「澳门底层数据建设」需求 |
| 非业务版本（worklog-template / v0.3.0） | 同样迁移，不丢 |
| 连续执行两次 | 第二次跳过，数据字节一致 |
| 迁移前存在备份 | 备份文件生成且可读 |

- MCP：
  - id 不存在 / 需求不属于该版本 / 版本已删除 → 明确报错；
  - `query_work` 按 versionId、requirementId、project、stage 过滤；
  - `list_versions` / `list_requirements` 输出 id 与计数。
- 服务层：版本/需求创建校验（重名、空名、关联项目不存在）、删除级联与备份、需求范围外改动提示。
- 前端：
  - 三级树展开/选中/复制 id；
  - 新建版本/需求后 toast 带复制按钮；
  - 四种知识库视图切换与「已关联/未关联」计数；
  - 删除版本需输入名称确认。
- 回归：现有 277 / 166 / 17 用例按新模型调整后全绿。
