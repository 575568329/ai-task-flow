# Phase 2:常驻对话 Runtime(持久化 + 流式体验)

> Mode A(看板与 Claude 协作对话)的第二阶段:把「每轮对话 spawn 一次 claude 进程」
> 升级为「同一会话常驻一个 claude 进程,连发复用,turn2 无冷启」。
>
> 适用范围:task 对话(`POST /api/tasks/:id/chat`)与 project 对话(`POST /api/project-chat`)。
>
> 完成时间:2026-07-25 | 提交链:6216444 → 05b9e9f → 9ffcb1a → df9b77e → cc1218a → 4913df5 → c6721bc

---

## 一、背景与问题

Phase 1 的对话接口走 `AgentRunner.run()`:**每个 turn 都 `spawn` 一个新的 claude 子进程**,turn 结束进程退出。实测痛点:

| 现象 | 原因 | 代价 |
|---|---|---|
| 连发第二轮明显卡顿(13s vs 4s) | 每轮冷启 claude 进程(SDK 初始化 + 加载) | 用户感知「越聊越慢」 |
| 中断(用户点停止)= 杀进程 | 进程退出,会话上下文丢失 | 再发必须 resume 重建 |
| 每轮 `--resume` 续接 | 进程不存活,只能靠 sessionId 重放 | resume 也有冷启开销 |

目标:**同一会话复用一个长期存活的 claude 进程**,push 消息驱动 turn,interrupt 不杀进程。

---

## 二、方案:Claude Agent SDK 的 streaming-input 持久模式

SDK 的 `query()` 支持 **streaming-input**:`prompt` 传入一个 `AsyncIterable<SDKUserMessage>`,只要这个输入流不 `end()`,**底层 claude 进程就常驻**。

```
传统(Phase 1):  query({ prompt: "单条文本" })  → 进程跑完即退
持久(Phase 2):  query({ prompt: inputStream })  → 进程常驻,executeTurn 时 push 一条消息
```

核心三假设(经 `spike/runtime-persistent` 实测成立):

1. **单次 `query({ prompt: inputStream })` 常驻**;`executeTurn` 时 push 一条 user message,turn 间**不 end**(end 会让 claude 判定会话结束退出)。
2. **`query.interrupt()` 只中断当前 turn,进程不死**(再发消息仍能收到 result);`query.close()` 才杀进程(= dispose)。
3. **首轮 result 的 `session_id`** 是 claude 分配的真实会话 id,据此把 runtime 从临时 key 迁移(rekey)到真实 key,后续连发命中复用。

实测数据:`spike` 中 turn0(冷启)≈13s,turn1(复用)≈4s,**省掉整个 SDK 冷启**。

## 三、架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│  HTTP 路由(taskChatRoutes / projectChatRoutes)                    │
│  POST → SSE:abortController.signal + onEvent=SSE.write           │
└──────────────────────────┬──────────────────────────────────────┘
                           │ executeTurn({ side, sessionId, cwd, text, signal, onEvent })
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  AgentRuntimeManager(池管理)                                       │
│  acquire → executeTurn → rekey → evict(on closed)                  │
│  signal.abort → runtime.interrupt                                  │
└──────────┬──────────────────────────────────────┬───────────────┘
           │                                       │
   ┌───────▼────────┐                     ┌───────▼────────┐
   │ RuntimeRegistry │                     │  AgentRuntime  │  (一个 = 一个 claude 进程)
   │ windows 池 / wsl │  acquire/get/set    │  consumeLoop   │  for-await query 输出
   │ GC sweeper(unref)│◄──────────────────►│  turnChain串行  │  routeMessage 路由
   └────────────────┘                     │  pending 单槽   │  push userMsg/turn
                                          └───────┬────────┘
                                                  │ query({ prompt: inputStream })
                                                  ▼
                                   ┌──────────────────────────────┐
                                   │ PushableInputStream(单 waiter)│  SDK 的 prompt 输入流
                                   └──────────────────────────────┘
```

**关键不变量**:
- **唯一消费者**:`AgentRuntime.consumeLoop` 是 query 输出流的唯一 for-await 消费者(构造时启动,dispose/crash 时结束)。
- **串行 turn**:同一 runtime 的 `executeTurn` 经 `turnChain` 排队,`pending` 单槽至多一个在途 turn(防覆盖)。
- **双侧隔离**:`RuntimeRegistry` 用两个独立 Map(windows / wsl),同 sessionId 不同 side = 两个 runtime(两个 claude 进程)。

## 四、核心组件

### 4.1 `PushableInputStream`(`application/agent/PushableInputStream.ts`)
SDK `query` 的 `prompt` 输入流。**单 waiter** 设计(SDK 只有一个消费者)。
- `push(message)`:executeTurn 时推一条 user message;turn 间**不 end**。
- `end()`:仅 dispose 时调(配合 `query.close()` 让 for-await done);幂等。

### 4.2 `routeMessage`(`application/agent/routeMessage.ts`)
SDK 输出消息(`SDKMessage`)的路由**纯函数**,分流三类:
| 路由 | 触发 | 处理 |
|---|---|---|
| `turnEnd` | `type==='result'` | consumeLoop 据此 resolve 当前 turn + 首轮取 session_id |
| `stream` | assistant / user / system(init) / thinking_delta | 透传 `onEvent`(→ SSE) |
| `ignore` | hook / text_delta / thinking_tokens 等噪音 | 丢弃(控 SSE 流量) |

> 与旧 `AgentRunner.shouldKeep` 同源过滤逻辑;`AgentRunner` 逐步废弃后统一到本文件。

### 4.3 `AgentRuntime`(`application/agent/AgentRuntime.ts`)
实现 `RuntimeRecord`,封装一个常驻 claude 进程。
- 构造即 `query({ prompt: inputStream })` + 启动 `consumeLoop`(后台,不 await)。
- `executeTurn(text, onEvent)`:经 `turnChain` 串行 → `runTurn` 设 `pending` + `inputStream.push(userMsg)` → consumeLoop 收到 result 时 resolve + 透传 onEvent。
- `interrupt()`:`query.interrupt()`(进程不死)。
- `dispose()`:`inputStream.end()` + `query.close()`(杀进程);reject 在途 turn;幂等。
- **crash 处理**:consumeLoop 的 for-await 抛错 → 标 `closed=true` + reject pending + 日志(Manager 据此 evict)。

### 4.4 `AgentRuntimeManager`(`application/agent/AgentRuntimeManager.ts`)
持有 `RuntimeRegistry`,提供 `executeTurn` 入口。
- **acquire 三分支**:已知 sessionId 命中复用 / 未命中新建并 `resume` 续接 / 新会话用临时 key(`__pending__<pid>_<seq>`)。
- **首 turn rekey**:runtime 真实 sessionId 落定后,把临时 key / 传入 id 迁移到真实 sessionId。
- **evict**:runtime `closed`(crash/dispose)→ 移除注册表所有相关 key,下次 acquire 重建。
- **signal 中断**:`signal.aborted` → `runtime.interrupt()`;turn 结束解绑 listener(后续 abort 不再触发已结束 turn)。

### 4.5 `RuntimeRegistry`(`application/agent/RuntimeRegistry.ts`)
双池 Map(windows / wsl)+ GC。
- `isStale` 纯函数:`closed` / 超绝对寿命(6h)/ 超空闲(30min)且无活跃 turn → 回收。
- `cleanupStale`:遍历 evict + 调 `record.dispose()`(失败也移除,坏 runtime 不卡 GC)。
- **sweeper**:`setInterval(...).unref()`,进程退出不阻塞;`startSweeper` 幂等。

### 4.6 `cleanSettings`(`application/agent/cleanSettings.ts`)
`CLEAN_SDK_SETTINGS = { hooks: {}, permissions: {allow:[],deny:[],ask:[]} }` 作为 **SDK flag 层**,覆盖 superpowers 的 SessionStart hooks/permissions 注入,隔离环境差异。`withCleanSettings(extra)` 浅合并调用方 settings。

## 五、关键决策与踩坑

### 5.1 ⚠️ clean settings:**保留 CLAUDE.md** 的隔离方式
- **错误做法**:`settingSources: []`(SDK 隔离模式)→ 干净,但**连带丢失 CLAUDE.md**,claude 失去项目上下文。
- **正确做法**:`settingSources` 保持默认(全读,含 CLAUDE.md),用 **inline `settings` 作为 flag 层**覆盖 hooks/permissions。
- 验证:`spike/clean-settings` 实测 `input_tokens=2`(superpowers 未注入),且 CLAUDE.md 仍生效。

### 5.2 ⚠️ result 必须**透传 onEvent**(否则前端卡死)
- **现象**:turn 结束,前端永远转圈「思考中」。
- **根因**:`routeMessage` 把 result 分流为 `turnEnd`,最初实现只 `resolve(executeTurn)`,**不调 onEvent**。但前端 `applyEvent` 靠 SSE 的 `result` 事件判断 turn 终态(`send()` 内处理)。
- **修复**:`consumeLoop` 的 `turnEnd` 分支在 resolve 前**先 `pending.onEvent(result)`**(AgentRuntime.ts:173-182)。
- **教训**:这类「数据流到没到前端」的 bug,**tsc 抓不到,只有端到端 curl 验证才发现**。集成后必须真实跑一次 SSE。

### 5.3 interrupt ≠ 杀进程
- `query.interrupt()`:中断当前 turn,claude 进程**存活**,当前 turn 以 `result(subtype=error_during_execution)` 正常 resolve,runtime 仍在池中供下次复用。
- `query.close()`:杀进程(= dispose)。
- 因此「用户点停止」= interrupt(复用),不是 dispose(重建)。

### 5.4 signal 覆盖中断,省独立 `/chat/interrupt` 端点
- 客户端断开(关抽屉/关窗)和前端「停止」**都是 abort fetch**。
- 路由层把 `request.raw.on('close')` 接到 `AbortController`,Manager 据 `signal` 调 `runtime.interrupt()`。
- 一套机制覆盖两种中断场景,无需单独的 `#6 interrupt` 端点(已并入 #5)。

### 5.5 双侧(Windows / WSL)隔离
- WSL 侧 `appendWindowsPath=false`,claude 装在 `~/.local/bin`,非 login shell 找不到 → 用 SDK 的 `spawnClaudeCodeProcess` 钩子 spawn `wsl.exe` 转发(`utils/sdk-loader.ts`)。
- Registry 按 `side` 分池:同 sessionId 在 windows 和 wsl 是**两个独立 runtime**(两个 claude 进程),互不串台(单测 `should_isolate_windows_and_wsl_pools` 覆盖)。

### 5.6 串行 turn(防 pending 单槽覆盖)
- 同一 runtime 并发 `executeTurn` 经 `turnChain` 排队,**前一个 settle 后下一个才开始**。
- `pending` 单槽:若不串行,第二个 turn 会覆盖第一个的 pending,导致第一个 turn 永不 resolve。
- `runTurn` 的 `.finally` **只**做 `activeTurnCount--` / `touch` / 计时日志,**绝不碰 pending**(由 consumeLoop/dispose/crash 唯一清),否则误清下一个已排队 turn。

## 六、GC 策略(`RuntimeRegistry`)

| 维度 | 阈值 | 常量 |
|---|---|---|
| 绝对寿命 | 6h(即使刚用过、有活跃 turn 也回收,防泄漏) | `RUNTIME_MAX_ABSOLUTE_LIFETIME_MS` |
| 空闲回收 | 30min 未用 **且** 无活跃 turn | `RUNTIME_MAX_IDLE_MS` |
| 扫描周期 | 5min(`setInterval.unref`) | `SWEEP_INTERVAL_MS` |

> 活跃 turn(`activeTurnCount>0`)时不回收,避免中断进行中的会话。
> 进程退出:`fastify.onClose` → `manager.shutdown()` → 停 sweeper + dispose 全部 runtime;sweeper 已 unref,SIGINT 直退靠 OS 清理。
