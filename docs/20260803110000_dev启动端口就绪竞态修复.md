# dev 启动端口就绪竞态修复

> 日期：2026-08-03
> 影响文件：`scripts/dev.ps1`
> 关联文档：[项目避坑与约定](20260723130001_项目避坑与约定.md) 一、端口与启动顺序

---

## 一、现象

`npm run dev` 启动后，前端页面打开但所有 `/api` 请求 404/无响应，看板数据加载不出来。后端日志却显示 `✓ Backend ready`，给人"后端起来了"的假象。

## 二、根因

`dev.ps1` 判断后端是否就绪的逻辑有**两个叠加缺陷**：

### 缺陷 1：用「端口文件存在」作为就绪信号——不可靠

原逻辑（第 75-80 行）：

```powershell
while ($waitedBackend -lt $maxWaitBackend) {
    if (Test-Path $portFile) { break }   # 文件在就认为后端好了
    Start-Sleep -Seconds 1
    $waitedBackend++
}
```

`backend-port.txt` 存在 ≠ 后端此刻可连。当 `tsx watch` 被 `shared/dist` 变化触发重启时：

- 端口文件可能是**上一实例**在重启前写的旧端口；
- 或写在重启间隙，而当前实例还没真正监听；
- 端口 3000 被外部进程占用时，backend 顺延端口的过程也会拉长这个窗口。

vite 代理若在此刻读端口文件，会落到错误端口 → 前端 API 全失败。

### 缺陷 2：等待超时后静默继续——掩盖失败

```powershell
Write-Host "Backend listening (waited ${waitedBackend}s)."
# ← 没有失败分支，无论等没等到都继续启动前端
```

30 秒超时后，无论后端有没有真正起来，dev.ps1 都会用默认端口启动前端。后端没起来时，前端就指向了一个无人监听的端口，表现为"前端在、API 全挂"的**静默崩溃**——用户完全不知道是后端的问题。

## 三、触发条件（复现路径）

```
端口 3000 被占用（其他 node 服务 / 僵尸进程）
  → backend 顺延端口 + tsx watch 被 shared 变化触发重启
  → backend-port.txt 写入延迟 / 写错
  → dev.ps1 等 30s 超时
  → 静默用默认端口启动前端
  → 前端连到无人监听的 3000 → API 全 404
```

## 四、修复方案

核心原则：**以「HTTP 实际可连」作为服务就绪的唯一真相（source of truth），不用间接标志。**

### 改动（`scripts/dev.ps1`）

**1. 两阶段就绪判定**

```powershell
# 阶段 1：等端口文件出现（拿到 backend 实际端口，可能因 3000 被占而顺延）
while ($waitedPort -lt $maxWaitPort) {
    if (Test-Path $portFile) { break }
    Start-Sleep -Seconds 1; $waitedPort++
}
if (!(Test-Path $portFile)) { Print-BackendLogTail; exit 1 }
$backendPort = (Get-Content $portFile).Trim()

# 阶段 2：HTTP 实际探测后端可连（消除「文件在但后端正重启」的竞态）
for ($i = 0; $i -lt 15; $i++) {
    try {
        $r = Invoke-WebRequest "http://127.0.0.1:$backendPort/api/tasks" -UseBasicParsing -TimeoutSec 2
        if ($r.StatusCode -eq 200) { $healthOk = $true; break }
    } catch { Start-Sleep -Seconds 1 }
}
if (-not $healthOk) { Print-BackendLogTail; exit 1 }
```

**2. 失败时即时反馈 + 退出**

新增 `Print-BackendLogTail` 函数：失败时直接把 `backend.log` 末尾 30 行打到终端，不甩文件路径给用户。无论阶段 1 还是阶段 2 失败，都 `exit 1`，绝不静默用错误端口启动前端。

**3. 启动摘要显示实际端口**

```
Backend:  PID 2796  -> http://localhost:3000 (/api 经 vite 代理到此)
```

## 五、验证

- ✅ 干净环境（3000 空闲）：backend 绑 3000，5s 内 HTTP 探测通过，前端正常代理。
- ✅ 后端不可达时：打印 `backend.log` 末尾 + `exit 1`，不再静默起前端。

## 六、通用教训（已记入 memory）

1. **就绪信号要用实际可连，不要用间接标志**——文件存在、进程存在、端口写出都可能是上一实例的残留或重启间隙的瞬态。
2. **超时/失败必须显式报错，禁止静默降级**——把"后端没起来"掩盖成"前端起来了但全报错"是最难排查的故障形态。
3. **失败时即时输出诊断信息**——别甩"请查某文件"，直接把日志末尾打出来；文件可能不存在、可能为空。

## 七、遗留 / 待观察

- 当 `shared/dist` 持续变化导致 `tsx watch` 反复重启时，15 次 HTTP 探测（约 15s）窗口可能不够。若复现"探测不可达"频繁，可考虑延长 `shared` 稳定等待（当前 2s）或增加探测次数。
- `scripts/dev.sh`（bash 版，非 Windows 用）有相同的"等端口文件"逻辑，本次未同步修改。Linux/mac 用户若遇到同类问题，需同步改造。
