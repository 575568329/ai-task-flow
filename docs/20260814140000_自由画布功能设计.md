## 〇、最终效果与功能清单（先看这个）

### 最终效果

把当前的**树形思维导图**升级为**自由画布白板**——类似 Obsidian Canvas / Heptabase 的轻量白板，但不局限于层级树。用户可以在无限画布上自由摆放文字、图片、链接卡片，任意方向连线组合成自己的知识/思路网络。

```
  ┌──────────┐         ┌────────────┐
  │ 文字节点  │────────▶│  图片节点   │   ← 双击空白创建 / 拖拽图片创建
  │ 双击编辑  │         │  可缩放     │   ← 任意方向自由连线（浮边）
  └──────────┘         └────────────┘
        │                     │
        │   ┌────────────┐    │
        └──▶│  链接节点   │◀───┘   ← 自由组合，不限树形
            │  点击跳转   │            ← 对齐辅助线辅助排版
            └────────────┘
```

**一句话定位**：个人自由记录画布——想到什么放什么，想连什么连什么，不受树形结构约束。

## 一、背景与目标

### 起因

当前思维导图模块是**纯树形结构**：节点只有 Left/Right 两个连接点，边路径硬编码为 Right→Left，层级关系（level/父子）在 UI 层强制。用户反馈：

> "我想要画布能够除了文字节点，可以双击生成节点，可以导入图片等自由链接，不局限于脑图。这个能做吗？节点四向自由链接，我就能自由组合去写内容。"

### 目标

将树形思维导图升级为**自由画布白板**，支持多种节点类型自由摆放、任意方向连线、图片/链接富内容，成为个人"想到什么放什么"的记录工具。

### 为什么能做（现状评估）

调研发现，**限制画布自由化的几乎全是 UI 交互层，数据模型早已支持**：

| 层 | 现状 | 是否阻碍自由化 |
|----|------|----------------|
| **数据存储** | `nodes[] + edges[]` 平坦数组（React Flow 原生图结构） | ❌ 不阻碍，已是图结构 |
| **领域聚合根** | 只校验边端点存在 + id 唯一，**不验证树形/无环/单根** | ❌ 不阻碍，已接受任意图 |
| **持久化** | `~/.ai-task-flow/mindmaps.json`，position 逐节点存储 | ❌ 不阻碍 |
| **图片上传** | `POST /api/upload/image` + base64 saver 已存在 | ❌ 不阻碍，直接复用 |
| **手动拖拽** | 拖拽位置已持久化 | ❌ 不阻碍 |
| **节点类型** | 仅 1 种 `mindmap` 文字节点 | ⚠️ 需新增类型 |
| **连接点** | 每节点仅 Left(target)+Right(source) 两个 handle | ⚠️ 需改浮边 |
| **边路径** | `BranchEdge` 硬编码 Right→Left | ⚠️ 需改动态交点 |
| **双击建节点** | 无 `onDoubleClick` 处理 | ⚠️ 需新增 |

**结论**：**领域聚合根 `MindmapDoc` 零改动**（不校验树形/类型），但需**新增独立的 canvas 应用层 / 持久化 / MCP / HTTP 子模块**。前端交互层是主要工作量，后端新增模块工作量可控。

## 二、竞品调研结论

详见附录。核心取舍如下：

### 该借鉴的

| 决策 | 来源 | 理由 |
|------|------|------|
| `nodes[] + edges[]` 平坦数组 + `node.type` 判别 | Obsidian Canvas / Excalidraw | **本项目已是此模型**，无需改 |

## 三、数据模型设计

### 设计原则

1. **平坦数组 + `node.type` 判别**（砍掉 `data.kind`，一个判别字段够——KISS）
2. **加字段非破坏**：现有 `MindmapNodeData` 已有 `[key: string]: unknown` 索引签名
3. **聚合根零改动**：`MindmapDoc` 仍把 nodes/edges 当不透明 blob
4. **边层零改动**：浮边模式下 handle 由算法动态算，数据结构不变

### 节点类型——统一用 `node.type` 判别（不引入 `data.kind`）

> **v3 修订**（审阅 S3）：React Flow 的 `node.type` 是天然渲染判别 tag（决定渲染哪个组件），无需在 `data.kind` 再放一个冗余字段。砍掉 `data.kind`，避免双轨判别困惑。

在 `shared/src/types/mindmap.ts` 的 `MindmapNodeData` 上扩展（向后兼容）：

```ts
export interface MindmapNodeData {
  // ===== 现有字段（保留）=====
  label: string;             // text 节点文本 / link 节点标题 / group 节点标签
  note?: string;             // 备注 / link 描述
  expanded?: boolean;        // 折叠状态（树形模式用）
  branch?: BranchKey;        // 分支配色（树形模式用，自由画布用 style.fill）
  level?: number;            // 层级深度（树形模式用）

  // ===== 新增字段（非破坏，node.type 判别节点种类）=====
  imageUrl?: string;         // image 节点：/api/uploads/xxx.png
  href?: string;             // link 节点：外链 URL
  width?: number;            // 可调尺寸节点（image/link/group）的自然宽
  height?: number;           // 可调尺寸节点的自然高
  style?: CanvasNodeStyle;   // 样式（语义 key，见第十三章）

  [key: string]: unknown;    // 索引签名（满足 RF Node<T> 约束）
}
```

**节点种类判别规则**：
- `node.type === 'mindmap'`（缺省）→ text 节点，渲染 `MindmapNode`
- `node.type === 'image'` → 渲染 `ImageNode`
- `node.type === 'link'` → 渲染 `LinkNode`
- `node.type === 'group'` → 渲染 `GroupNode`
- `node.type === 'embed'`（远期）→ 嵌入 task/canvas/mindmap

**向后兼容**：旧文档 `node.type` 全是 `'mindmap'`（或缺省），加载后全部按 text 渲染，行为完全不变。

### CanvasNodeStyle（样式语义 key）

```ts
/** 节点标记色——shadcn 语义 key 或 chart 分类 key */
type CanvasFill = 'default' | 'primary' | 'secondary' | 'destructive' | 'muted'
  | 'chart-1' | 'chart-2' | 'chart-3' | 'chart-4' | 'chart-5';

interface CanvasNodeStyle {
  fill?: CanvasFill;            // 语义标记色或中性分类色
  borderStyle?: 'solid' | 'dashed';
  borderWidth?: 'thin' | 'thick';
  rounded?: boolean;
  fontSize?: 'sm' | 'md' | 'lg';
}
```

### 边（连线）

现有 `MindmapFlowEdge`（`source/target/sourceHandle/targetHandle/data`）已足够。浮边模式下 `sourceHandle/targetHandle` 由 React Flow 自动写入，浮边渲染时忽略具体值。

```ts
export interface MindmapFlowEdge {
  // ...现有字段不变
  data?: { branch?: BranchKey; label?: string }; // 新增可选 label（连线标签）
}
```

### 不引入的东西（对比 tldraw/Excalidraw）

- ❌ `data.kind` 字段——用 `node.type` 统一判别（KISS）
- ❌ 独立 binding record（tldraw 式）——React Flow 浮边自动跟随
- ❌ `normalizedAnchor` / `fixedPoint`——浮边算法处理
- ❌ `version` / `versionNonce` / `isDeleted`——单人不协作

## 四、数据保存设计

### 设计原则

1. **文件即数据**（Obsidian 模式）：JSON 明文，可 git diff、可云盘同步
2. **媒体引用不嵌入**：节点存 URL，二进制在 `uploads/`（避免 JSON 膨胀）
3. **schemaVersion 版本化 + 迁移机制**：版本号配 `applyMigrations()` 函数
4. **round-trip 容忍**：未知字段原样保留（前端渲染态透传不丢）

### 存储格式（P0 保持单文件，P2 再 per-doc）

> **v3 修订**（审阅 S4）：per-doc 分片降级 P2（YAGNI——图片是 URL 引用不内嵌，单文件体积增长有限；且 MCP 经语义层不直接碰文件，per-doc 的"agent 直读"动机不成立）。P0 保持现有单文件 `mindmaps.json` + 加 `schemaVersion`。

```
~/.ai-task-flow/
├── mindmaps.json              ← 现有单文件，加 schemaVersion（P0）
│                                P2 演进为 canvases/<id>.json + index.json
├── uploads/                   ← 现有，图片资产（复用）
│   └── <hash>.png
```

`mindmaps.json` 结构（现有 + schemaVersion）：

```json
{
  "schemaVersion": 1,
  "documents": [
    {
      "id": "624350df-...",
      "title": "Ecode 运行脑图",
      "version": 150,
      "nodes": [ /* node.type='mindmap'/'image'/'link'/'group' */ ],
      "edges": [ /* data.label 可选 */ ],
      "viewport": { "x": 0, "y": 0, "zoom": 1 },
      "createdAt": "ISO",
      "updatedAt": "ISO"
    }
  ]
}
```

> `schemaVersion` 放在 repository 包装层（聚合根 `MindmapDoc` 保持纯净，不改 toJSON/fromJSON）。`assets` 索引是 repository save 时从 `nodes[].imageUrl` 派生的冗余索引，前端/agent 永不直接写。

### schemaVersion 迁移机制

```ts
// infrastructure/persistence/migrations.ts
const MIGRATIONS = [
  { from: 0, to: 1, migrate: (doc) => doc }, // v0→v1: 加 schemaVersion，数据无变化
  // 未来: { from: 1, to: 2, migrate: (doc) => { /* per-doc 拆分等 */ } }
];

function applyMigrations(doc: unknown, currentVersion: number): unknown {
  return MIGRATIONS
    .filter(m => m.from >= currentVersion)
    .reduce((d, m) => m.migrate(d), doc);
}
```

在 `JsonMindmapRepository` 的 `fromJSON` / `loadAll` 时调用。`schemaVersion` 缺省视为 0。

### P2 per-doc 分片（远期）

当单文件真的过大时，演进到 `canvases/<id>.json` + `index.json`。必须配套：
- 迁移脚本 + 自动备份 `mindmaps.json.bak.<timestamp>`
- 读时迁移 + 旧文件保留（标记 `.migrated`）
- 幂等可重跑 + 回滚测试
- `index.json` 降级为可重建缓存（目录扫描校正）

### 跨进程并发安全（关键）

> **v3 新增**（审阅 S1）：MCP server 是独立 stdio 进程，`withWriteLock` 是进程内 mutex，两进程互不可见。agent 写 + 用户同时拖 = lost-update。

**方案：MCP 写收口 HTTP API**

```
Agent → MCP 工具 → HTTP API (localhost:PORT/api/canvas/...) → HTTP 进程内 withWriteLock → 文件写
Agent → MCP 工具 → 直读文件（只读安全）
```

- MCP 写操作（create/update/delete）**经 HTTP API 调用**，不直接写文件
- MCP 读操作（list/read）**直读文件**（只读无并发风险）
- 所有写收口到 HTTP 进程，复用其 `withWriteLock`
- 前端检测到外部变更（watcher 推来）且本地 dirty 时，提示"画布已被 agent 修改"

### 资产管理

- **复用 `POST /api/upload/image`**：图片存 `~/.ai-task-flow/uploads/<random>.<ext>`
- **节点存相对 URL**：`data.imageUrl = "/api/uploads/xxx.png"`
- **assets 索引**：repository save 时从 `nodes[].imageUrl` 派生（前端/agent 不直接写）
- **孤儿清理（P2）**：扫描所有画布 assets 索引，删无引用上传文件

### 向后兼容

- 旧 `mindmaps.json`（无 `schemaVersion`）→ 视为 v0，`applyMigrations` 升到 v1（无数据变化）
- 新字段 `imageUrl/href/style` 缺省不影响旧文档
- `node.type` 全是 `'mindmap'`（旧文档）→ 按 text 渲染

## 五、Agent 可操作设计（核心）

### 核心原则：不暴露原始 JSON

**调研铁律**：原始画布 JSON 对 Agent 是毒药。VaultForge MCP 实测——15 节点画布，**语义图 ~200 tokens，原始 JSON ~2000+ tokens（10 倍）**。MCP 工具设计为**语义层**：读返回摘要，写接受语义描述 + 自动布局。

### MCP 工具清单（snake_case，经 HTTP 写）

> **v3 修订**（审阅 S6/S7/B7）：① MCP 写经 HTTP API 不直写文件（跨进程安全）；② `create_canvas` 的 nodes 支持可选 id 供 edges 引用；③ MCP 不走 expectedVersion（agent 串行，force update）；④ 布局用 shared DFS 不引入 dagre；⑤ P1 先做 6 个核心工具。

| 工具 | 入参 | 出参 | 说明 |
|------|------|------|------|
| `list_canvases` | `{}` | 画布清单表 | 浏览现有画布 |
| `read_canvas` | `{ canvasId, detail?: 'summary'\|'full' }` | summary：语义图（label+连接，无坐标）；full：含坐标 | **默认 summary 省 token**；full 有节点数阈值警告 |
| `create_canvas` | `{ title, nodes: [{id?, label, type?}], edges: [{from, to, label?}], layout?: 'LR'\|'TB'\|'free' }` | 画布 id | nodes 可选 id（供 edges 引用），不传则后端生成；layout≠free 用 shared DFS 自动算坐标 |
| `update_canvas_node` | `{ canvasId, nodeId, label?, type?, imageUrl?, href?, note?, style? }` | 更新结果 | force update（不走 expectedVersion） |
| `connect_canvas_nodes` | `{ canvasId, from, to, label? }` | 连线结果 | 连两节点 |
| `delete_canvas_node` | `{ canvasId, nodeId }` | 删除结果（连带边） | |
| `get_canvas_screenshot` | `{ canvasId }` | 渲染截图（base64 PNG） | **P1**：感知验证，让 agent 自查布局质量 |
| `create_from_mermaid` | `{ title, mermaid }` | 画布 id | **P2**：前端实现（不后端引入 mermaid） |
| `save/restore_canvas_snapshot` | `{ canvasId, snapshotId? }` | 快照 id / 还原结果 | **P2**：含快照存储设计 |

**P1 MVP 子集**：list + read(summary) + create + update + connect + delete + screenshot（7 个）。mermaid/snapshot 降 P2。

### create_canvas 节点引用语法

> **v3 新增**（审阅 S6）：明确 edges 的 from/to 引用规则。

```json
{
  "title": "系统架构",
  "nodes": [
    { "id": "n1", "label": "前端" },
    { "id": "n2", "label": "后端" }
  ],
  "edges": [
    { "from": "n1", "to": "n2", "label": "API 调用" }
  ],
  "layout": "LR"
}
```

- nodes 支持可选 `id`（agent 可传人类可读临时 id 如 `n1`，不传则后端生成）
- edges 的 `from`/`to` 用该 id
- 写进 MCP schema description（agent 靠 description 理解用法）

### 自动布局

> **v3 修订**（审阅 S2）：不引入 dagre（后端没装 + 前端已弃用），复用 shared DFS。

`create_canvas` 的 `layout` 参数：
- `LR`（左右树）/ `TB`（上下树）：用 **shared DFS 布局**（从 `layout.ts` 抽到 shared，前端/后端/MCP 共用），agent 不需要懂坐标
- `free`：默认 fallback 到 LR（agent 给坐标大概率堆叠）

### MCP ↔ 前端同步

现有 `TaskFileWatcher` 用 `fs.watchFile`（轮询单文件，跨进程可靠）。canvas 复用同模式：
- P0（单文件）：watcher 监听 `mindmaps.json`（现有 TaskFileWatcher 可扩展或新建）
- P2（per-doc）：监听 `index.json` 单文件（任何文档变更更新 index 的 updatedAt），前端按 index 变化全量重拉
- 延迟预期 ~1-2s（单文件），per-doc ~2-3s

### MCP 写收口 HTTP

> **v3 新增**（审阅 S1）：MCP 工具的写操作经 HTTP API 调用（`http://localhost:PORT/api/canvas/...`），不直接实例化 repository 写文件。读操作直读文件（安全）。

## 六、导出导入设计

### 设计原则

- **导出 = 单文件自包含**（zip），可云盘/邮件传输
- **导入 = 还原**，含图片物化（解压到 uploads + 重写 URL）
- **格式透明**：zip 内就是标准 JSON + assets/

### 导出格式：zip 包

> **v3 修订**（审阅 B6）：zip 库选 `adm-zip`（纯 JS、API 简单）；assets 文件名强制 `<hash>.<ext>`（避免中文乱码），原始 name 存 manifest.json。

```
画布标题.canvas.zip
├── canvas.json          ← JSON Canvas 格式（schemaVersion + nodes + edges）
├── assets/              ← 引用的图片（文件名强制 <hash>.<ext>）
│   ├── <hash1>.png
│   └── <hash2>.jpg
└── manifest.json        ← { formatVersion, exportedAt, canvasTitle, assetCount, originalNames }
```

导出流程：

1. 读画布文档
2. 扫描 nodes 中所有 `imageUrl`，收集 assets
3. `/api/uploads/<hash>.png` → `assets/<hash>.png`（相对路径重写）
4. `adm-zip` 打包 + 前端触发下载

### 导入流程

> **v3 修订**（审阅 B6）：导入校验 zip bomb（总字节上限 + 文件数上限 + 路径穿越防护）。

1. 上传 zip（`POST /api/canvas/import`，multipart）
2. **安全校验**：解压后总字节 ≤ 50MB、文件数 ≤ 100、路径无 `..` 穿越
3. 校验 `manifest.json` 的 `formatVersion`
4. `assets/` 图片 → 写入 `~/.ai-task-flow/uploads/`（按 URL 字符串判重，已存在跳过）
5. 重写 `imageUrl` 从 `assets/<hash>.png` → `/api/uploads/<hash>.png`
6. 生成新 id → 保存

### 不做

- ❌ 单文件 base64 内联所有图片（JSON 膨胀）——用 zip
- ❌ 加密导出——YAGNI
- ❌ 跨工具格式互通——非目标

## 八、连线设计（浮动边）

### 问题

当前 `BranchEdge` 硬编码 `sourcePosition: Position.Right` / `targetPosition: Position.Left`，自由布局下连线方向错乱。

### 方案：浮动边（官方 FloatingEdge 模式）

照搬 React Flow 官方 `examples/FloatingEdges` 的几何算法：

1. **每个节点只放 1 个 source handle**（浮边忽略具体 handle 位置）
2. **`BranchEdge` 改用动态交点**：根据 source/target 节点中心连线与各自包围盒的**交点**计算起止坐标和方向
3. **`ConnectionMode.Loose`**：允许任意 handle 互连
4. **measured 空值兜底**：新建节点首帧 `measured` 未填充时 `getEdgeParams` 返回 null，避免 NaN

### 核心文件

> **v3 修订**（审阅 S11）：`FloatingConnectionLine` 是**自写组件**（非 RF 内置），必须补到文件清单。

| 文件 | 说明 |
|------|------|
| `floatingEdgeUtils.ts` | **新增**：`getNodeIntersection` / `getEdgePosition` / `getEdgeParams`（照搬官方） |
| `BranchEdge.tsx` | 改用 `getEdgeParams` 动态交点 + `measured` 兜底 |
| `FloatingConnectionLine.tsx` | **新增**（自写）：拖拽连线时的临时连线走同一算法 |

### 自环/重复边拦截

> **v3 新增**（审阅前端遗漏）：`onConnect` 加 `if (conn.source === conn.target) return;` + 已存在边检查。

### 效果

- 节点怎么摆，连线都从最近的边出发
- 节点移动/缩放时连线**自动跟随**
- 完全替代 tldraw 的独立 binding record

## 十二、设计取舍与不做项

### 为什么选 Obsidian Canvas + React Flow 浮边

| 维度 | 本方案 | tldraw/Excalidraw |
|------|--------|-------------------|
| 数据复杂度 | nodes+edges ~6 字段 | record map + binding + asset + version ~20 字段 |
| 实现量 | 前端 ~14 文件 + 后端 ~10 文件 | 引擎级，需 signals/sync/migration |
| 协作 | 不需要 | 核心能力（但本项目不需要） |
| 手绘 | 不支持 | 核心能力 |
| 适合场景 | 个人本地自由记录 | 协作白板/手绘 |

### 不做项（明确排除）

1. **手绘画笔**——非场景需要；若将来要，嵌 tldraw 子组件
2. **多人协作/实时同步**——单人本地，YAGNI
3. **节点富文本（Yjs 协同编辑）**——YAGNI
4. **用户侧约束求解自动排版**——保留现有树形自动布局（agent 创建时可用 shared DFS）
5. **节点内嵌 React Flow（画中画）**——复杂度爆炸

### 关键取舍

| 取舍 | 决策 | 理由 |
|------|------|------|
| `data.kind` vs `node.type` | **统一用 `node.type`** | KISS，RF 天然判别 tag（审阅 S3） |
| per-doc vs 单文件 | **P0 单文件，P2 再 per-doc** | YAGNI，图片是 URL 引用体积有限（审阅 S4） |
| MCP 直写 vs 收口 HTTP | **写收口 HTTP** | 跨进程并发安全（审阅 S1） |
| dagre vs shared DFS | **shared DFS** | 后端没装 dagre + 前端已弃用（审阅 S2） |
| 卡片跨画布复用 | **不做（每画布是孤岛）** | YAGNI，单人够用（审阅 Q3） |
| 模式切换 | **加 `docMode: 'tree'\|'canvas'`** | 消除认知混乱（审阅 B12） |

### branch 与 style.fill 渲染优先级

> **v3 明确**（审阅 B10）：当节点同时有 `branch` 和 `style.fill` 时，**`style.fill > branch > default`**。

### 向后兼容保证

- `node.type` 全是 `'mindmap'`（旧文档）→ 按 text 渲染，行为不变
- 现有 `data.branch/level/expanded/note` 全保留（树形模式用）
- 新字段 `imageUrl/href/style` 缺省不影响旧文档
- `schemaVersion` 缺省视为 0，`applyMigrations` 升级

## 十三、UI 与交互设计

> 设计依据：Excalidraw `snapping.ts`（8px 阈值）、tldraw `alignShapes`/`distributeShapes`、Excalidraw `COLOR_TOP_PICKS`、社区 snapGrid 共识。
>
> **现状评估**：完全空白——无 snapToGrid、无对齐线、节点单行不换行；8 色 branch 配色只给 level-1 分支节点着色。

### 13.1 网格与背景

| 项 | 现状 | 设计值 | 说明 |
|----|------|--------|------|
| 变体 | 点阵 Dots | **保留点阵** | 最不干扰视觉 |
| gap | 18px | **20px** | 对齐 snapGrid |
| size | 1.5 | 1.2 | 略小更干净 |
| 可切换 | 无 | **加"显示网格"开关** | 大图排版时关掉 |

### 13.2 吸附系统（两层）

#### 第一层：snapToGrid（粗对齐，P1）

```tsx
<ReactFlow snapToGrid={showGrid} snapGrid={[20, 20]} />
```

默认关闭，联动网格开关。

#### 第二层：对齐辅助线（细对齐，P0）

> **v3 升级 P0**（审阅 S9）：文档自证"解决 80% 排版"，自由画布无自动布局兜底，对齐线是唯一排版支撑。

| 项 | 设计值 | 依据 |
|----|--------|------|
| 阈值 | **8px ÷ zoom** | Excalidraw + tldraw 共识 |
| 对齐类型 | 左/右/上/下边缘 + 水平/垂直中心 | 同 Excalidraw |
| 等距吸附 | 相邻间距相等时吸附 | **P2**（额外 40-60 行） |

**实现**（自研，RF 无内置）：
- `onNodeDrag` 拦截 + `getNodesBounds()` 比较拖动节点 6 条参考线与其余节点
- 阈值内修正坐标 + 渲染 SVG `<line>`
- **helperLines 用本地 `useState`，不进 Zustand**（否则拖 200 节点全量 re-render）
- ~75 行（基础版）

### 13.3 节点边框（必须有）

自由画布节点密集摆放，无边框会糊成一团。保留 1px border，颜色跟随节点配色。

### 13.4 节点样式系统（与 shadcn 统一）

> **设计原则**：画布节点是 shadcn 主题的自然延伸，颜色是"语义标记"不是"装饰彩绘"。

#### 问题：两套色系脱节

| 色系 | 彩度 | 风格 | 用在哪 |
|------|------|------|--------|
| shadcn 语义色 | 0.007~0.042 | 克制中性灰 | 全项目 UI |
| branch 8 色 | 0.13~0.18 | 鲜艳彩色 | 仅思维导图 |

#### 统一方案

**① 默认节点 = shadcn card 原样**（`bg-card text-card-foreground border`）

**② 标记色 = shadcn 语义 tint**（强调用）：

| fill 值 | 语义 | 渲染（color-mix 半透明 tint） |
|---------|------|-------------------------------|
| `default`（缺省） | 无标记 | 纯 card |
| `primary` | 重点 | `bg-primary/10 border-primary/30` |
| `secondary` | 次要 | `bg-secondary border-secondary/40` |
| `destructive` | 警示 | `bg-destructive/10 border-destructive/30` |
| `muted` | 弱化 | `bg-muted border-muted-foreground/20` |

**③ 分类色 = shadcn chart 色**（中性分类用，审阅 B4）：

> **v3 新增**：语义 tint 带语义负担（primary=重点），不适合做"技术/产品/运营"分类。补 `chart-1~5`（Tailwind 数据可视化分类色，与 shadcn 同源不违和）。

| fill 值 | 渲染 |
|---------|------|
| `chart-1` ~ `chart-5` | `color-mix(in oklch, var(--chart-N) 15%, var(--card))` + border tint |

**④ branch 8 色保留给树形模式**（自由画布不用）

#### 完整样式维度

| 样式维度 | 选项 | 默认 |
|----------|------|------|
| 标记色 | default/primary/secondary/destructive/muted + chart-1~5 | default |
| 边框样式 | 实线 / 虚线 | 实线 |
| 边框宽度 | 细 / 粗 | 细 |
| 圆角 | 开 / 关 | 开 |
| 字号 | 小 / 中 / 大 | 中 |

**不做**：roughness、fillStyle（hachure）、透明度滑块、自定义 hex 取色器。

### 13.5 排列工具（P1）

多选时浮动工具栏：6 对齐（左/中/右/上/中/下）+ 2 分布（水平/垂直等距）。纯前端 `getNodesBounds()` 计算。

### 13.6 节点尺寸与换行（P0）

| 项 | 现状 | 设计 |
|----|------|------|
| 换行 | 不换行 | **whitespace-normal + max-width 280px** |
| 长文本 | 无 | 双击进入编辑模式，高度自适应，max-height + 溢出滚动 |
| 缩放 | 不可 | `<NodeResizer>`（resize 中不调 markDirty，onNodeDragStop 才调） |

### 13.7 数据模型：data.style（语义 key）

```ts
type CanvasFill = 'default' | 'primary' | 'secondary' | 'destructive' | 'muted'
  | 'chart-1' | 'chart-2' | 'chart-3' | 'chart-4' | 'chart-5';
```

**用语义 key 而非 hex 的理由**：与项目 UI 统一、agent 语义更强、主题自动正确。

渲染映射（CSS）：

```css
.mm-card[data-style="primary"] {
  background: color-mix(in oklch, var(--primary) 10%, var(--card));
  border-color: color-mix(in oklch, var(--primary) 30%, var(--border));
}
/* secondary / destructive / muted / chart-1~5 同理 */
```

`color-mix(in oklch)` 浏览器支持：Chrome 111+/Firefox 113+/Safari 16.2+（2026 年全量覆盖 3+ 年，无风险）。

### 13.8 Agent 可操作策略

| 操作 | style 处理 |
|------|------------|
| `read_canvas` summary | **不返回 style**（省 token） |
| `read_canvas` full | 返回 style（语义 key） |
| `update_canvas_node` | 接受 `style: { fill: 'destructive' }` |
| agent 批量建图 | 默认无 style |
