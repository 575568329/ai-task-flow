## 决策项 2 ｜ tsyringe 去留（P1-12）

**问题**：`di/container.ts` 只注册 2 个 token 且都被 `useFactory` 绕过；HTTP 入口完全不用 container（`http-server.ts` 手工 `new` 13+ 个 service 透传）；`@injectable()` 装饰器挂在多个 Repository 上却几乎无人 `resolve`。这套「半套 DI」既没换来解耦，又增加阅读成本，违反「如无必要勿增实体」。

更糟：MCP 进程与 HTTP 进程装配不对称——MCP 用 `container.resolve('TaskRepository')` 拿到一个**没注入 eventBus/eventStore/watcher 的默认实例**，与 HTTP 进程操作同一文件却互不通信。

**选项**：

| 选项 | 动作 | 成本 |
|------|------|------|
| **A（推荐）** | **移除 tsyringe**，统一手工装配；MCP 进程改用与 HTTP 同一份 startApp 装配 | ~0.5 天 |
| B | 真正用起来：把 startApp 装配搬进 container，HTTP+MCP 共享一份 resolve 入口 | ~1 天 |

**我的推荐：A。** 手工装配已全且清晰，DI 当前是纯负担。移除后 MCP/HTTP 装配不对称问题一并解决。

**请回复**：A / B。

## 决策项 3 ｜ ClaudeProfile token 下发意图（claude-profile 🟡 中等/安全）

**问题**：`ClaudeProfileService.toSummary`（约 237–246 行）把含**明文 AUTH_TOKEN** 的完整 `settings` 下发前端，与该文件头注释「只返回脱敏视图」**矛盾**。

**需你确认产品意图**：

- **情形 A（故意）**：profile 编辑器需要回填用户自己粘贴的完整 settings（含 token）供再次编辑/导出。若如此，前端编辑页是「用户看自己的 token」，风险可控，但应：(1) 前端明确提示「含敏感凭证，勿在共享屏幕展示」；(2) GET 列表接口仍只给脱敏视图，仅「编辑单个」接口给原值。

**我的判断**：从 `ClaudeProfilePanel.tsx` 的编辑流程看更像情形 A（用户管理自己的 claude settings 快照）。但文件头注释说「脱敏视图」与之矛盾，需你拍板到底要哪个语义。

## 决策项 4 ｜ lockfile 是否入库（P1 关联）

**问题**：`.gitignore` 排除了 `package-lock.json`，理由注释是「跨内网/公网 resolved 源来回变」。代价：CI 无法 `npm ci`（只能 `npm install` 重新解析）、依赖漂移风险全靠人工、不同机器装出版本可能不一致。

**选项**：

| 选项 | 利 | 弊 |
|------|----|----|
| A（现状，不入库） | 内网/公网切换不冲突 | 无可复现安装、CI 弱 |
| **B（推荐）** | 入库 + 统一公网源（移除 `.npmrc` 的国内镜像硬编码，改各自 `.npmrc` 本地覆盖） | 可 `npm ci`、依赖锁定 | 初次提交需统一一次源 |

**我的推荐：B。** 这是 P1-8（加 CI）的前置——没有 lockfile，CI 的「可复现构建」就是空话。若你短期不想动 lockfile，CI 可先用 `npm install` 起步，但建议尽快补。

**请回复**：A / B（或暂缓，CI 先用 install）。

## 决策项 5 ｜ AgentRuntime bypass 权限策略（P0-1，源码核实后移入待审批）

**背景修正（重要）**：核实发现 `AgentRunner.ts` 已是死代码（全仓库 0 生产调用方），真正生效的 bypass 在 `AgentRuntime.ts:108-109`（`permissionMode: 'bypassPermissions'` + `allowDangerouslySkipPermissions: true`）。

**批次 2 已根治远程攻击面**：HTTP 默认 host 收敛到 `127.0.0.1` + system 路由非本机拒绝后，外部已无法访问危险接口。bypass 剩下的风险只是「本机用户让 claude 全权执行」——这是个人本地工具的设计意图，不再是远程漏洞。

**问题**：bypass 是否要改为 opt-in 默认关？

| 选项 | 动作 | 利 | 弊 |
|------|------|----|----|
| **A（推荐）** | 保持默认开 + 加 warn 日志（每次旁路留痕） | 个人工具体验顺滑，claude 自动执行不卡顿 | 本机恶意网页 CSRF 仍能触发（需用户先访问恶意页 + 服务无鉴权） |
| B | 改 opt-in 默认关 + 前端「信任模式」开关 | 纵深防御更强 | claude 每个需权限操作卡住等确认，需配套前端开关 + settings 宽松规则，体验成本高 |

**我的倾向：A**。host 收敛后风险可控，bypass 是个人工具核心体验。若你更看重纵深防御（担心本机恶意网页），选 B。

**请回复**：A / B。
