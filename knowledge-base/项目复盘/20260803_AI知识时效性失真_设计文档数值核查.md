# AI 知识时效性失真：设计文档中的"具体数值"必须核查

> **一句话**：LLM 写"概念 / 架构 / 权衡"基本可靠，但一旦落到**具体数值**（版本号 / 窗口大小 / 库的支持范围 / "XX 就是这么做的"实现细节），训练截止后的变化它不知道，却会**流畅地编一个看起来合理的数**——这类断言是设计文档的核查红线。
>
> **来源**：ECode 项目（手写 AI coding agent）写 M3 上下文管理设计文档时的真实翻车案例。

---

## 一、现象：一份设计文档里的数据全是错的

ECode 的 M3 阶段要做"上下文管理"（token 计数 + 压缩）。我（AI）凭既有知识写了两份设计文档（实施方案 + 方案解析），用户审阅时发现**涉及具体数值的地方几乎全错**：

| 断言类型 | AI 写的（错） | 核查后（对） | 错在哪 |
|---------|------------|------------|--------|
| 模型上下文窗口 | GLM-5.2 ~128k | GLM-5=200K / **GLM-5.1+=1M** | 用了旧版本数据 |
| 模型上下文窗口 | DeepSeek ~64k | V3/V3.1/R1=128K / **V4=1M** | 同上，且漏了新出的 1M 模型 |
| 库的支持范围 | ai-tokenizer "覆盖 GLM/DeepSeek" | **无原生 encoding** | 排他性断言失真 |
| 库的能力 | ai-tokenizer "90+ 模型" | 捏造 | 纯属编造，无此数据 |
| 库的准确率 | ai-tokenizer "97%+" | 仅限顶级模型，第三方测评有争议 | 只采信厂商宣传 |
| 实现机制 | "Claude Code/opencode 用 80% 百分比阈值" | Claude Code 用**绝对 token 数 167K**（≈83.5%） | 机制理解错 |

**关键**：这些错误不是"偶发失误"，而是**同一类**——都是"快速变化的具体数值"。抽象部分（为什么要压缩、压缩要保护 tool 配对、判别联合怎么用）全是对的。

---

## 二、根因：为什么 LLM 在"具体数值"上必翻车

### 1. 训练数据有截止日期

模型窗口、库版本、支持范围这类数据**变化极快**（DeepSeek 半年内从 64k → 128k → 1M）。LLM 的训练快照停留在某个时点，之后的变化它根本没见过。

### 2. LLM 不会说"我不知道"

对这类问题，LLM 的行为不是诚实地说"这个我不确定"，而是：
- 从旧知识里找一个"看起来合理"的数
- 用同样流畅、自信的语气写出来
- **越具体越自信**——精确到数字、带"覆盖/支持 XX"的排他性断言，读起来最像真的

### 3. 抽象 vs 具体的可靠性分界

| 可信（变化慢） | 不可信（变化快） |
|--------------|----------------|
| 概念解释（什么是 BPE / 上下文窗口） | 某模型某版本的窗口大小 |
| 架构模式（分层 / Provider 抽象） | 某库支持哪些模型 |
| 设计权衡（精确 vs 粗估的取舍） | 某项目的某行代码"就是这么写" |
| 协议原理（tool_use 配对约束） | 某工具的具体阈值数值 |

**规律**：越是"具体到某时某刻的某数字"，越要核查；越是"通用原理"，LLM 知识越可靠。

---

## 三、核查方法：三源核查 + 出处标记

设计文档中凡涉及**具体数值 / 库支持范围 / 协议机制**，走三源核查：

### 源 1：源码（最高可信）

本地有的源码库派子代理逐行核实，引用 `file:line`。
- 例：查 Claude Code 怎么算 token → `claude-code-main/services/tokenEstimation.ts:203-208`，看到就是 `length/4`。
- 例：查压缩阈值机制 → `messages.ts` 里看到绝对 token 数 167K，不是百分比。

### 源 2：官方文档 / 模型卡

WebSearch 查一手数据：模型窗口（Atlas Cloud / 阿里云 / OpenRouter）、库的 supported models 列表、API 协议约束（Anthropic 官方 GitHub issues）。

### 源 3：第三方测评（对抗厂商宣传）

厂商声明（如"97% 准确率"）不照单全收，找独立测评交叉验证。
- 例：ai-tokenizer 官方说"≥97%"，dev.to 第三方测评显示部分模型仅 37.7% within 10% → 结论是"官方数据仅适用顶级模型"。

### 核查产物：出处标记

每个数值 / 实现断言带 `file:line` 或 URL 出处（正文用 📌 标记），让读者能复验。**没出处 = 没核查 = 不可信**。

## 四、通用原则（可执行清单）

> **写设计文档时的自检：当我要写下一个精确数字、或一句"XX 支持/覆盖 XX""XX 就是这么做"时，停下来问——"这个我核查过吗？出处是哪？"答不上来就去查，别凭记忆写。**

### 开工前

- [ ] 识别文档里的"高风险断言"：所有具体数值、版本号、库支持范围、实现细节
- [ ] 对每个高风险断言标注出处（`file:line` / URL / 官方文档）

### 写作中

- [ ] 触发警觉的信号词：精确数字、"支持/覆盖/兼容 XX"、"XX 就是/都是这么做的"、具体阈值
- [ ] 抽象内容（概念/架构/权衡）可凭知识写，但落地的具体参数必须核查

### 验收时

- [ ] 用户审阅前，AI 自查：每个 📌 标记是否都有真实出处？
- [ ] 用户重点抽查：随机挑几个数值，问"这个在哪看到的？"

## 五、与其他 AI 盲区的关系

本条是 [[20260701_AI协作开发通用原则]] 的补充，与其中两条同源但不同质：

- **通用原则 #3「AI 过度信任局部信息」**：AI 看到**部分符号**就下结论（看到变量名推断接口位置）。——那是**当前视野内的证据不足**。
- **本条「知识时效性失真」**：AI 的**训练数据本身过时**，它"以为知道"的数值其实是错的。——这是**知识库层面的问题**，跟当前视野无关。

两者都会导致"流畅地编"，但诱因不同：#3 是"没看全"，本条是"记的是旧的"。防治手段也不同：#3 靠"看完整依据链"，本条靠"三源核查 + 出处标记"。

## 六、附：ECode 本次核查修正的具体数据

供其他项目参考（核查时间 2026-08-03，数据本身仍会变，**引用前请重新核查**——这正是本条原则的自我应用）：

- **GLM 系列**：GLM-5 = 200K / GLM-5.1+ = 1M（ECode 配置默认 `glm-5.2` = 1M）
- **DeepSeek 系列**：V3 / V3.1 / R1 = 128K / V4 = 1M
- **Claude Code token 估算**：`length/4`（`tokenEstimation.ts:203-208`）
- **Claude Code 压缩阈值**：绝对 token 数 167K（≈200K 窗口的 83.5%），非百分比
- **Claude Code 压缩方式**：LLM 生成 9 段总结（非滑动窗口），prompt 见 `prompt.ts:61-143`
- **Anthropic 配对约束**：tool_use/tool_result 必须配对，孤立则 API 400（GitHub #5662 / #8004）
- **ai-tokenizer 准确率**：官方"≥97%"仅适用 GPT-5/Claude/Gemini；第三方测评部分模型 37.7% within 10%
